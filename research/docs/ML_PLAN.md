# 0. Встреча с экспертами (16.09) — уточнения и практические выводы

Протокол совещания по >130 вопросам. Разделы ниже — изменения к нашему плану.

## 0.1 Определения отказа и уровня агрегации
- **Отказ — это цепочка**, а не только датчик:
  `датчик → шина → питание → контроллер → модем → оператор связи → линия → сервер`.
  Отказ элемента может «уронить» группу датчиков/линию.
- **Три класса датчиков** (влияет на фичи и цель):
  1. **Бинарные** — «тревога/нет» → анализ последовательностей и связей между датчиками;
  2. **Цифровые** — числовые значения → временные тренды (температура, метан, CO, O₂), превышения порогов;
  3. **Логические домены** — несколько датчиков как единая система (подтверждение тревоги согласованным срабатыванием).
- Уровень агрегации (канал/объект/инж. система/инфраструктурная цепочка) — по-прежнему нерешённая проблема данных.

## 0.2 Метрики и горизонт (смягчение ТЗ)
- Precision 0.7 / Recall 0.5 — **стартовые значения по умолчанию, НЕ жёсткие**. Можно свои пороги с обоснованием.
- Обе метрики важны; одной приоритетной не названо.
- **Горизонт 24ч — дефолт, не абсолют.** Допустимы 1/6/24/48/несколько горизонтов одновременно (у нас уже есть 09: 6/12/24/48ч).
- Leaderboard: до топ-10 доступен только факт «прошли/нет»; итоговая оценка экспертная (модель + интерфейс + полнота решения), поэтому упаковка и демо критичны.

## 0.3 Данные — прояснения
- Глубина **~7.5 лет**, не 12 — техническая несовместимость старых версий БД/ключей. Объёма достаточно (сезонность, режимы).
- **2021 — переходный период** (одновременно работали разные версии систем, рост тревог без роста инцидентов): можно исключить / выделить период / нормализовать / добавить признак переходного периода.
- **Аномальные значения** (−100, 255, MAX целочисленного поля, резкие выбросы) — коды производителя/контроллера: решаем сами (удалять / NaN / флаг «тех. ошибка» / оставить) и фиксируем выбор.
- **Канал→объект подтверждён**: обновлённый справочник каналов содержит `ид_объект`; старый составной тег (`p1-p2.p3...`) возник при обезличивании и в решении **не нужен**.
- Гео не обязательны: схематичная линейная карта + пикеты (шаг 10 м, для демо можно другой шаг); МСК — при желании.

## 0.4 Источники меток — обновлённые ожидания
- **Журнал ОДС** = диспетчерский HelpDesk (объединение событий в заявку, отслеживание до устранения, **нет прямой интеграции событие→заявка**, решение принимает человек). → потенциальный источник разметки после восстановления ключей/правил связывания, **НЕ готовый ground-truth**.
- **Подтверждение «ложно/реально»** добавляется человеком на объекте и может добавляться там же, где создаётся инцидент → наш сервис обязан собирать подтверждения (это будущие метки для дообучения).
- **История частичных ремонтов узлов не ведётся**; возраст ≠ фактическое состояние; нормативный срок — не метка износа. Допускается использовать усреднённые показатели наработки из открытых источников (проверить на реалистичность).
- Визуальная метка «нужен ремонт» (обследования ОЭ) как формальный источник — **не подтверждена**.
- Планы пикетов / ТО-ППР отдельным источником не представлены (будущие журналы дефектов/испытаний/отключений/ремонтов).

## 0.5 Новые/обновлённые модельные направления
- **Доступ**: одиночный сигнал = не проникновение. Положительная эвристика — **последовательность событий**:
  дверь/люк → объёмный датчик → движение в соседней зоне, пространственно-временная согласованность.
  Ложно скорее: один объёмный в середине коллектора, нет входов рядом, нет последующих событий.
  Камеры не интегрируются (только ручная проверка оператором).
- **Пожар**: метки нет → **риск-скоро** (инж. система + тренды температуры + дым/тепло вне кампаний + сезон/календарь). «Температура >100°C» может быть сваркой/локальным нагревом/пожаром — нужны объяснение и карточка.
- **Подтопление** (новый пример от экспертов): протечка → вода по уклону → затопление соседнего коллектора → частые вкл/выкл насоса (характерная последовательность) → детектировать по паттернам включений насосов/затоплений.
- **Трендовая модель для цифровых датчиков** (температура/газ): тренды, превышения порогов — отдельный пайплайн value-фич.

## 0.6 MVP и поставка (что реально нужно показать)
- MVP: меньше функций, но проработанные: **карточка прогноза/инцидента** (объект, инж. система, канал, тип риска, вероятность, горизонт, факторы риска, история, рекомендуемое действие, превентивная заявка, подтверждение/отклонение), интерфейс диспетчера, журнал прогнозов, REST API.
- Разрешены: эмуляторы событий, демо-роли, тестовая авторизация, синтетические данные (реалистичные, не «случайные числа»).
- Оценка: полный запускаемый пакет + документация + **видео-демо** настоятельно рекомендовано; объяснимость и практическая ценность важны не меньше метрик.

Приложение 1 описывает live-схему СМВУ (журнал + реестры). Она отличается от выгрузок `.7z`, но легко маппится:

**Что добавляет Приложение 1 (ценно):**
- **Тип канала как отдельная сущность** — подтверждает стратификацию моделей по типу датчика (у нас `тип_датчика`).
- **Диспетчерские названия типов** — семантика, которой нет в числах телеметрии.
- **Дерево объектов/инженерных систем** — готовый каркас признаков «объект/система» (пожарная система, вентиляция, камера, шкафы).

**Гипотезы для проверки на данных:** покрытие журналов реестром (уже проверено — 99.9%), стабильность id каналов (сменяются ли), один датчик ↔ один канал.

**Обновление по итогам встречи с экспертами (16.09):**
- **`ид_объект` подтверждён** — обновлённый справочник каналов содержит его; связь канал→объект восстановлена.
- Старый составной тег `тег_инженерной_системы` (`p1-p2.p3...`) возник при обезличивании — в решении его можно игнорировать, как основной ключ объекта использовать `ид_объект`.
- Гео-координаты не обязательны: схематичная линейная карта коллекторов + пикеты (`p3`, шаг 10 м — для демо можно другой).


## 2. Главный вопрос: сколько моделей?

**Короткий ответ: НЕ одна модель на всё и НЕ модель на каждый датчик.**

| Вариант | Оценка | Аргументы |
|---|---|---|
| 1 модель на всё (11.5k каналов разом) | ✗ | Разные физики сигналов (дым vs температура vs телеметрия 0.00/0.01), разные цели и пороги. Одна модель «усредняет» и теряет и пожары, и отказы. |
| Модель на каждый датчик (~11.5k моделей) | ✗ | Нет данных на обучение единичных каналов, нет холодного старта, MLOps-оверхед, переобучение на шум. |
| **Субмодель на каждый ТИП датчика (8–12 моделей)** | ✅ рекомендуется | Одна физика → один набор признаков, одна целевая, один порог. Данных по типу достаточно (дым — 4.3k каналов). |
| Модель на группу датчиков объекта | ⚠ частично | Нужна как верхний уровень агрегации для дашборда (правила), но не как базовый предиктор. |

### Итоговая архитектура (трёхуровневая пирамида)

```
         ┌──────────────────────────────────────────────┐
         │  L2. Агрегация на уровень ОБЪЕКТА (дашборд)   │
         │  правила/бустинг поверх L1-рисков;            │
         │  «индекс риска объекта» для карты и алертов   │
         └──────────────────────┬───────────────────────┘
                                │
         ┌──────────────────────▼───────────────────────┐
         │  L1. Модели по ТИПАМ датчиков (ОСНОВНАЯ)      │
         │  smoke / gas / temperature / movement /       │
         │  contact(КД) / pump / fan / phase / прочее    │
         │  Каждая: свои признаки + своя цель + порог    │
         └──────────────────────┬───────────────────────┘
                                │
         ┌──────────────────────▼───────────────────────┐
         │  L0. Общий слой: нормализация + признаки      │
         │  пер-канальные z-скор, «фоновая телеметрия»,  │
         │  календарь кампаний, признаки ПК/объекта       │
         └──────────────────────────────────────────────┘
```

**Почему «модель на каждый датчик» привлекательна, но не нужна:** «персональность» датчика дают признаки z-score по истории самого канала, скользящие средние, категории `ид_канала_данных`/`коллектор`/`ПК`. Новые датчики работают через модель своего типа (холодный старт).

## 2.1. Стекинг «глобальная по типу» + «локальная по объекту» (0.7 : 0.3)

**Идея (от команды):** для датчиков одного типа на объекте учить **локальную суб-модель (объект-специфичную)** и стекать её с глобальной моделью типа с пониженным весом:

```python
score_final = 0.7 * model_type_global.predict_proba(X)[1] \
            + 0.3 * model_object_local.predict_proba(X)[1]
```

**Почему это хорошо:**
- **Глобальная модель типа** знает «типовую» физику дыма/газа/движения, работает для всех объектов, включая холодный старт.
- **Локальная модель объекта** выучивает «характер» конкретного коллектора: возраст парка, специфику монтажа, фоновые шумы (847 с 933 дымовыми ведёт себя иначе, чем 16 с 276).
- Стек 0.7/0.3 устойчив: если локальная переобучится или объект мал — глобальная «держит» качество. Веса подбираем на валидации (поиск по сетке 0.5..0.9 для глобальной).

**Проверка на данных (сделана):**
- 32 уникальных коллектора (`p1` из тега);
- **29 из 32** имеют ≥1 тип датчика с ≥10 каналами (локальная выборка обучаема);
- 6 коллекторов покрывают **11 типов** датчиков сразу (847: 933 дымовых, 105 УИР-Р, 67 фазы, 59 КД Двери, 55 газа, 54 движения…);
- **104 группы (тип × коллектор) имеют ≥30 каналов** → полноценные локальные модели.

**Условия активации локальной модели:**
1. `count(каналов типа на объекте) >= N_local` (рекомендую 30);
2. история событий объекта ≥ 90 дней;
3. иначе — только глобальная: `score = 1.0 * model_type_global`.

**Риски и смягчение:**
- Малые объекты → «локальная» переобучится → порог N_local + регуляризация;
- дрейф парка (рост 5.6k→11.5k) → локальная модель переучивается на обрезке (последние 2–3 года);
- новый объект — локальной нет, берём глобальную + медианные статические признаки.


## 2.2. Контекст объекта (признаки «соседних» датчиков)

**Идея (от команды):** обучать модель канала на признаках не только самого канала, но и **соседей по объекту** — чтобы модель знала «контекст» объекта (идут ли работы рядом, задымление соседних ПК, массовое ТО).

**Признаки контекста (для канала i в момент t):**
- `neighbor_alarm_rate(i,t)` — доля тревог среди других каналов того же коллектора за окно (6ч/24ч);
- `neighbor_fault_rate(i,t)` — доля статусов «Неисправен/Обесточен» на объекте;
- `neighbor_similar_type_rate(i,t)` — то же по каналам **того же типа** на объекте (ближний контекст);
- `same_pk_alarm(i,t)` — тревога в соседнем пикете (из `p3`), особенно для дыма/газа;
- `object_work_flag` — по календарю кампаний/планам ТО объект в работе;
- лаговые версии (сдвиг 24ч/7д).

**Реализация:** агрегируем по `(объект=коллектор, окно)` на уровне признаков L0 и добавляем колонки к каждому каналу объекта — одним проходом (группировка по `p1`), без отдельной модели.

**Почему усилит качество:**
- Пожарный риск: дым рядом с горячими работами/соседними сработками;
- Несанкционированный доступ: движение в соседнем ПК одновременно = маршрут нарушителя;
- Износ: массовое ТО у соседей = плановые работы, а не отказ.

**Ограничение:** контекст добавляет колонки → фиксируем список контекст-фич в model card для интерпретации (SHAP) и мониторинга дрейфа.

| 7 | Погода/сезон | Для температуры и износа | ⚠ внешние метеоархивы (бесплатно) |
| 8 | Реестр ОЭ (даты ввода, фонды) | Возраст → износ | ⚠ возраст/норматив рассчитать можно; допускается усреднённая наработка из открытых источников; метка «нужен ремонт» не подтверждена |

Без пунктов 5–6 модель всё равно обучаемая, но целевая метка определяется по косвенным статусам («Неисправен», «Обесточен», «Затоплен»), а не по журналу ремонтов. Фиксируем это допущение явно.

### Допущения по целевой переменной (ground truth)

1. **«Отказ датчика в ближайшие 24 ч»** = появление у канала статусов «Неисправен»/«Обесточен»/«Отключено устройство» в окне +24 ч. ✱ кампании исключены.
2. **«Пожарный риск»** = тревога дыма/газа/тепла в окне +24 ч, исключая кампании проверок.
3. **«Несанкционированный доступ»** = тревога движения/КД в нерабочее время без корректного допуска (данные АРМ-Контроль).
4. **«Износ»** = рост частоты неисправностей/отказов насоса/вентилятора + возраст + погода (модель второго порядка).

### Уточнения экспертов (16.09) к допущениям
- Отказ — цепочка «датчик→шина→питание→контроллер→модем→канал→сервер»; «неисправность» канала — прокси, допустимый для обучения.
- Для **бинарных** датчиков цель событийная (серия/первая тревога); для **цифровых** (температура, газ) — тренды значений и превышения порогов.
- Доступ: положительная эвристика — **последовательность** (дверь/люк + объёмный + движение соседней зоны); одиночный сигнал — не положительный.
- Пожар: подтверждённой метки нет → «риск-скоре» с объяснением (температура >100° ≠ пожар).


## 4. Пайплайн признаков

### 4.1. Агрегация в окна
События датчика → ежечасные агрегаты: счётчик событий, доля тревог, доля «шума» (0.00/0.01/смены состояния), доля неисправных статусов, средние/медианы значений. Окна: 6ч, 24ч, 7д, 30д + скользящие средние/std/тренд/мин/макс.

### 4.2. Пер-канальная нормализация
`z = (x - медиана_канала_90д) / (MAD_канала_90д + eps)`; «доля от фона» для частоты событий.

### 4.3. Статические
Тип датчика, инж. подсистема, коллектор `p1`, пикет `p3`, `p5` из тега; категории объекта; возраст (если появятся даты ввода); `ид_канала_данных` как категория (при достаточном объёме).

### 4.4. Контекст объекта
Признаки соседей по объекту (раздел 2.2) + флаги кампаний/плановых работ + час/день/сезон.

### 4.5. Горизонт и валидация
- Горизонт: **24 ч — дефолт**; допускаются 1/6/12/48ч и несколько горизонтов одновременно (реализовано в `09_wear_horizons`).
- Сплит: **временной** (train ≤ 2024, val = 2025, test = 2026), **кампании исключены** (`data_utils.filter_clean_weeks`).
- **2021 — переходный период** (несколько версий систем одновременно): исключать/нормализовать/добавлять признак переходного периода.
- Метрики: Precision ≥ 0.7, Recall ≥ 0.5 — стартовые значения по умолчанию (обоснованные отклонения допустимы); дополнительно PR-AUC, корригированные на базу (lift), калибровка (isotonic/logistic per type).
- Дефицит класса — только train-овский SMOTE/class_weight.
- Аномальные значения (−100/255/MAX) — коды производителя: обработка (удалять/NaN/флаг/оставить) фиксируется явно.


## 5. Поставка и интеграция с бэкендом

1. **8–10 моделей L1** + локальные (тип × объект) + агрегатор L2 → joblib/pmml/ONNX, конфиг порогов на тип.
2. **Inference API**: `predict(channel_id, history_window)` → `(риск, вероятности, top_factors, порог_типа, метаданные)`.
3. **Model card** на каждый тип и на каждую локальную группу: цель, фичи, метрики, ограничения, калибровка.
4. **Обновление**: переобучение по мере пополнения журналов (+ **подтверждений диспетчера** — они становятся реальной разметкой); мониторинг дрейфа (PSI по фичам, ECDF по вероятностям).
5. **Холодный старт**: новый датчик/объект → модель типа + медианные статические признаки.
6. **MVP-фокус (по итогам встречи 16.09)**: меньше функций, но проработанные — **карточка прогноза/инцидента** (объект, инж. система, канал, тип риска, вероятность, горизонт, факторы риска + «почему», история, рекомендуемое действие, превентивная заявка), подтверждение/отклонение прогноза, журнал прогнозов, REST API. Эмуляторы событий и демо-роли допустимы. Обязательны видео-демо и запускаемый пакет.
7. **Объяснимость**: топ-факторы и причинно-следственная подсказка (напр. «рост температуры ≠ пожар: возможна сварка/локальный нагрев»).

## 6. Риски и ограничения

- **Целевая метка косвенная** (нет журнала ремонтов) → только устойчивые статусы, экспертные верификации.
- **Кампании** исключены, но могут повториться → мониторинг дрейфа + календарь.
- **Неравномерность парка** (5.6k→11.5k) → нормализация по числу активных каналов.
- **Редкие типы** (стекло, затопление — 25 каналов) → «модель прочего», не отдельные.
- **Время инференса < 5 мин** — пайплайн на агрегатах (не сырых) укладывается с запасом; тяжёлые фичи — по расписанию.


## 8. Выбор моделей (по уровням)

### Контекст, влияющий на выбор
- Целевой класс **редкий**: доля тревог в чистых неделях 0.2–0.5% (медиана 0.34%), в кампаниях — до 17.7%. → нужны дизбаланс-устойчивые алгоритмы + классовая взвешивание + подбор порога по PR-кривой, а не по accuracy.
- Признаки — **агрегаты** (счёты/доли/скользящие статистики), частично категориальные (тип, коллектор, ПК), много пропусков («канал молчал» = окно без событий) → градиентный бустинг как базовый класс подходит лучше, чем гладкие нелинейки вроде MLP (нет надобности в топологии).
- Горизонт 24ч, инференс < 5 мин на объект — табличный ML с предпосчитанными фичами легко укладывается.

### L1 — главные модели по типам датчиков

| Алгоритм | Плюсы | Минусы | Решение |
|---|---|---|---|
| **LightGBM** | быстрый, справляется с пропусками (`NaN` как «нет событий»), category-фичи, `is_unbalance`/`scale_pos_weight`, калибровка простая | переобучение на малых типах | ✅ **базовый** для всех типов |
| **CatBoost** | силён на категориальных + дизбаланс, OrderedBoost | медленнее, странна на больших датасетах | ✅ сравнить на типах с богатой категориальной структурой (Дым, КД) |
| XGBoost | зрелый, но категориальные требует кодировки | — | резерв |

**Пакет для каждого типа (кратко):**
1. **Глобальная по типу**: LightGBM (по умолчанию) + CatBoost (кандидат сравнения) → выбираем по валидационной PR-AUC/Precision-Recall.
2. **Локальная по объекту** (если N≥30 каналов): LightGBM малого размера (max_depth 3–4, сильная регуляризация) ИЛИ, для очень малых групп — LogisticRegression на нормализованных фичах (устойчивее к переобучению). Стек 0.7·global + 0.3·local.
3. **Калибровка**: IsotonicRegression на out-of-fold вероятностях **per тип** (с учётom распределения порогов). При малых выборках — Platt scaling.
4. **Порог**: выбирается по PR-кривой под целевые Precision ≥ 0.7 / Recall ≥ 0.5, с допуском по обоим.

### L2 — агрегация на уровень объекта (дашборд)

| Подход | Когда | Оценка |
|---|---|---|
| Правила: max/сумма топ-k канальных рисков | для старта, интерпретируемо | ✅ v1 |
| Логистическая регрессия на перцентилях канальных рисков объекта | когда правил не хватит | ⚠ после правила |
| Лёгкий LightGBM на «свёртке» канальных рисков | конечная цель | 🔜 поэтапно |

Правила L2 проще: `index_object = w1*max(canal_risks) + w2*top3_mean(risks) + w3*тревога_за_24ч`, пороги — экспертные, калибровка не нужна.

### Сравнение альтернатив (зачем не LSTM/Transformer/Prophet)

| Модель | Почему НЕ берём в основной контур |
|---|---|
| LSTM/GRU/Transformer (TFT) | Требует авторегрессионную цель на сыром ряду; при нашем объёме (11.5k каналов × часы) и почти-бинарном сигнале выигрыш над LGBM фичами мал, рисков переобучения больше, интерпретируемость хуже. |
| Prophet/сезонная декомпозиция | Это тренды одного ряда без ковариат; у нас много ковариат (типы, соседи, кампании) — бустинг их использует лучше. |
| «Дальний» ансамбль (GBM + DNN) | Оправдан только если LGBM-CV покажет потолок; дорого. |

**Ограничение метода (важно для бэкенда):** бустинг даёт **вероятность**, а не «когда именно» +24ч. Горизонт 24ч — это скалярная цель «событие в следующие 24h», модель не выдаёт распределение времени. Если потребуется «в какое время» — отдельная задача (multi-horizon/временной point process) — вне v1.

### Метрики и протокол сравнения
- Основные: **PR-AUC**, Precision@Recall≥0.5, Recall@Precision≥0.7, калибровка (ECE/изотonic fit), PR-кривая на тесте 2026 с исключением кампаний.
- Сплит: временной (train ≤ 2024, val = 2025, test = 2026); дополнительно — временной CV с шагом недели.
- Дизбаланс: `scale_pos_weight = neg/pos` (или class_weight), только на train; SMOTE — резерв для редких типов.
- Определяем «потолок» случайной модели и majority-class baseline для каждого типа.


## 9. Валидация и построение обучающего датасета

### 9.1. Формат датасета: «канал × день, цель вперёд»

**Одна строка = (ид_канала_данных, дата t).**

- **Фичи** считаются ТОЛЬКО по данным **строго до t**: окна `[t-6ч, t)`, `[t-24ч, t)`, `[t-7д, t)`, `[t-30д, t)`.
- **Цель** — событие-мишень в `[t, t+24ч)`: бинарный флаг (напр. «Неисправен в следующие 24ч»).

**Критично про утечку (data leakage):**
- окно фич и окно цели не пересекаются (фичи < t, цель ≥ t);
- в фичи НЕ попадает значение в самой точке t;
- мишень не используется как признак;
- кампании (2021W17–W22) вырезаются из всех сплитов.

**Размер (оценка по данным):**
- 2024: ~533 тыс. пар (канал,дата); 2021: ~565 тыс.; всего ~4.2–4.5 млн строк за 8 лет — укладывается в RAM (1–2 ГБ с фичами).
- Медиана событий на пару = 2–3 (разреженность) → включение «тихих» дней как негативов обязательно (это большинство).

### 9.2. Схема построения панели (шаги)

1. **Сырые события → суточные агрегаты (channel-day)**: на каждую пару: `count_events`, `count_alarms`, `count_fault` («Неисправен»/«Обесточен»/«Отключено устройство»), `count_noise` (0.00/0.01), `count_status` по типам, средние/медианы числовых значений, `ноль_событий` флаг.
2. **Скользящие признаки по каналу** (groupby channel → sorting по дате → rolling):
   - счётчики за окна [1д, 3д, 7д, 14д, 30д];
   - нормированные на канал: `x / median_канала_30д`, z-score;
   - отношения «недавнее/обычное»: `events_7d / events_30d`, `alarms_7d / alarms_30d`;
   - тренды: наклон событий за 7д (Theil-Sen/полином), ускорение;
   - тишина: max-разрыв между событиями за 7д, доля дней с 0 событий за 30д.
3. **Контекст объекта** (из 2.2): те же окна по группе `p1` (доля тревог/неисправностей соседей, `same_pk_alarm`).
4. **Статические** (по справочнику): тип, подсистема, `p1/p3/p5`, возраст (если появится).
5. **Merge** всего в единый DataFrame c колонками `[канал, дата, фичи..., цель]`.

### 9.3. Валидация (временная, а не случайная!)

- **Основной сплит:** train ≤ 2024 → val = 2025 → test = 2026. Кампании исключены.
- **И никакого случайного `train_test_split`!** Ряды зависимы во времени.
- **Walk-forward (роллинг)**: дополнительно оцениваем на нескольких срезах
  (напр. train до Tᵢ, val = Tᵢ+1, по 5–6 срезам) — устойчивая оценка и CV-бейзлайн.
- **Purge/Embargo**: из train убрать строки, чьи 30-д.-окна фич пересекают границу val —
  иначе временные признаки «подсмотрят» будущее.
- **Additional check — cold start**: отложить по каналам (например, каналы, появившиеся в 2025–2026)
  — проверить обобщение на новые датчики/объекты.
- Метрики считаем по «чистым» неделям только, с группировкой по типам датчиков.

### 9.4. Целевые переменные (кратко, обновлено по итогам встречи 16.09)

| Направление | Цель (бинарная, в окне +горизонт) | Определение / статус |
|---|---|---|
| Отказ датчика | «Неисправен/Обесточен/Отключено устройство» появился у канала | статусные счётчики ≥1 — прокси; отказ = цепочка «датчик…сервер»; для бинарных — событийная цель, для цифровых — тренды значений |
| Пожарный риск | риск-скоре (метки нет) | инж. система + тренды температуры + дым/тепло вне кампаний + сезон/календарь; «температура>100°» ≠ пожар — нужна объяснимость |
| Несанкц. доступ | **последовательность** событий | дверь/люк + объёмный + движение соседней зоны (пространственно-временная согласованность); одиночный сигнал — не положительный |
| Подтопление | эвристическая последовательность | протечка → затопление соседнего коллектора → частые вкл/выкл насоса (паттерн включений) |
| Износ | рост частоты неисправностей насосов/вентиляторов | модели 2-го порядка; возраст — из реестра ОЭ/открытых источников наработки (проверить реалистичность) |

Для редких типов (движение, насос) возможно объединение нескольких смежных дней в цель:
«событие в t..t+3д» для увеличения положительного класса (с пометкой в model card).

### 9.5. Подтверждения как будущая разметка
- Сервис обязан собирать **решения диспетчера** (подтвердить/отклонить прогноз, ложная/инцидент) — это единственный путь к настоящим меткам (журнал ОДС — HelpDesk без интеграции; разметку добавляет человек на объекте).
- Модели размечаем эвристиками (серии/цепочки/риск-скоры), метрики считаем по «чистым» неделям, в model card — честные ограничения по ground-truth.

## 0.1. Суть проблемы текущего слоя 2

В `10_wear_series.ipynb` слой «дней до события» — **ор-динальный мультикласс**
по 8 бин-классам (≤0.5д … >30д) с классом «>30д/цензур» как обычным классом.

Концептуальные недостатки:
1. **Не учитывается цензурирование корректно**: строки без будущего события в
   данных кладутся в класс «>30 дней» как наблюдаемые, хотя это right-censoring.
2. **Одна точка** (ожидаемые дни = Σ p(класс)·mid) вместо **распределения S(t)**.
3. Метрика MAE по серединам бинов смещена и не робастна к цензуре.
4. Два слоя (P(события в горизонт) и «дни до») обучаются независимо и не
   согласованы между собой.

Целевое состояние: модель выдаёт **кривую выживаемости S(t)** (для 6ч/12ч/24ч/
48ч/7д/14д/30д), из которой выводятся и P(событие ≤ H), и медиана/ожидаемые дни,
и интервалы — единый слой вместо двух.

## 1. Быстрые выигрыши (низкий риск, ~1–2 дня)

### 1.1. Правильное кодирование цензуры
- Формат разметки: `(время_наблюдения, событие_flag)`.
- Событие: `days = dist_to_event`, `event = 1`.
- Нет будущего события: **административная цензура** на фиксированном горизонте
  (напр. t+30д): `days = 30`, `event = 0`.
- Убирает главное искажение текущего «>30д» класса.
- Библиотеки: `lifelines`, `scikit-survival` (`Surv.from_arrays(event, time)`).

### 1.2. Честные метрики (в дополнение/вместо MAE)
- **C-index / concordance**: `sksurv.metrics.concordance_index_censored` (или
  `lifelines.utils.concordance_index`) — робастна к цензуре.
- **IPCW Brier / integrated Brier**: `sksurv.metrics.brier_score`,
  `integrated_brier_score` — качество распределения.
- **Медиана выживаемости** (`lifelines.utils.median_survival_times`) + интервалы.
- MAE — только справочно, по нецензурированным строкам.

### 1.3. Якорные базовые модели
- **Kaplan-Meier / Nelson-Aalen** по типам каналов (фон риска).
- **lifelines**: `CoxPHFitter`, `WeibullAFTFitter` — интерпретируемый baseline и
  источник «базового hazard» для фич; проверить PH-допущения.

## 2. Основной апгрейд: дискретно-временная hazard-модель (person-time)

Идеально подходит нашим 6-часовым бакетам (аналог pycox `LogisticHazard`/
Nnet-survival, но на CatBoost, без нейросети):

1. Каждую строку (канал, бакет) «раздвинуть» во время → person-time датасет:
   - шаги t = 1..K; метка = 1 в бакете события, 0 на всех предыдущих шагах;
   - после события и за цензурой строки не включаются.
2. Добавить фичи времени: «часов/бакетов до конца горизонта», час, день недели,
   месяц — модель учит **hazard P(событие в шаг t | дожил до t)**.
3. CatBoost логистический → `S(t) = ∏(1 − ĥ)`:
   - `P(событие в 24ч) = 1 − S(24ч)` — **объединяет слой 1 и слой 2**;
   - медиана/ожидаемые дни и интервалы из S(t).

Плюсы: корректная цензура, распределение, переиспользует готовый пайплайн фич и
CatBoost. Минусы: датасет вырастает в ~K раз (K=40 бакетов на 10 дней → ~64 млн
строк): ограничить горизонт 7–14 днями и/или прореживать риск-сеты.

## 4. Фич-инжиниринг для дня-события

- **Горизонт-зависимые признаки**: окна 3/7/14/30д — другие, чем для бинарного
  24ч; отношение «событий за 7д / событий за 30д»; `time_since_last_series_start`;
  длина текущей серии.
- **Эмпирический фон риска**: пер-типовой/пер-объектный сглаженный KM/hazard-профиль
  как фича (учёт гетерогенности каналов, без ручной разметки).
- **Событийные последовательности**: число стартов серий за 1/7/30д, «частые
  старты → ближе следующий», паттерны вкл/выкл насосов (сценарий подтопления).
- **Цифровые датчики** (когда дойдём): тренды значений, flatline, время выше
  порога — критично для дня-события на цифровых типах.

---

## 5. Калибровка и продукт

- Калибровать S(t): isotonic per time-bin / Platt; проверять IPCW-Brier.
- Продукт: карточка с **кривой выживаемости** (S при 6ч/12ч/24ч/48ч/7д),
  медианой и P(≤H) — решение диспетчера по распределению, а не по точке.

---

## 6. Валидация

- Walk-forward + **административная цензура** на 30 дней.
- Метрики ТОЛЬКО с учётом цензуры: C-index, IPCW-Brier (+ MAE справочно).
- По типам/объектам отдельно (неравный парк каналов).

---

## 7. Рекомендуемая последовательность работ

1. **День 1–2**: правильная цензура + KM-якорь + C-index/IPCW-Brier на текущем
   слое → честные цифры вместо MAE.
2. **День 2–4**: **person-time hazard на CatBoost** (главный апгрейд) → S(t),
   P(24ч), медиана; сравнить с текущим ор-динальным слоем.
3. **День 4–5**: XGBoost AFT и CatBoost Cox как независимые бенчмарки; выбор по
   C-index + Brier.
4. **Опционально**: pycox `LogisticHazard`/`MTLR`; фич-апгрейд (фон риска,
   гетерогенность, последовательности).

# Часть III. Продуктовая рамка MVP (CBM / RBAM / RUL)

# План: ядро MVP в канве индустриальных стандартов (CBM / RBAM / RUL)

Версия: 0.1 · Дата: 20.09.2026 · Автор: ML Research + Product

## 0. Резюме (зачем этот план)

Измерения на 7.5 годах СМВУ (holdout ≥ 2025-07-01) показали:

- **24-часовое «раннее предупреждение ПЕРВОГО события» на чистых строках не работает**
  для fire (PR-AUC 0.03), sensor (0.012), access (0.03): события редкие (база 0.3–1.5%),
  нет журналов ОДС/АРМ-Контроль/СКУД;
- при этом **ранжирование и распределения времени сильны**: Uno-C 0.72–0.79,
  risk30 хорошо калиброван (wear/fire), exp_days (медиана дней) работает;
- эксперты (16.09) смягчили ТЗ: горизонт 24ч — «дефолт, не абсолют», Precision 0.7/Recall 0.5 —
  «стартовые, не жёсткие», оценка экспертная (упаковка > сухих метрик);
- мировая и РФ-практика (Siemens ResilOps/PlantSight, Thames Water+Samotics
  condition-based monitoring, RBAM-обзор Springer, «Цифровой водоканал»,
  NIST по ложным тревогам) действует так же: **состояние → риск → приоритет → план**,
  а не «час отказа».

**Решение:** ядро MVP переформулируем вокруг «приоритизации и планирования
профилактики» (CBM + RBAM + RUL). Исходные критерии ТЗ не выбрасываем —
они переводятся в **резервный (fallback) сценарий** «буква ТЗ» и демонстрируются
там, где сигнал реально есть (wear, fire топ-K), на случай, если заказчик
настоит на прежней постановке.

## 1. Ядро MVP (новое)

**Одна фраза:** сервис отвечает не «что сломается через 24 часа?», а
**«где риск прямо сейчас и что делать в ближайший план ТО?»**.

### Сценарий 1 — Риск-карта (view)
- Топ-риски по объектам/каналам: риск30, медиана дней (exp_days), уровень риска,
  факторы («почему») — топ-фичи + сезон/календарь.
- Карточка прогноза: S(t) кривая (RUL-распределение), P(≤24ч) как вторичная цифра с пометкой
  «низкая различимость первого события», рекомендуемое действие, превентивная заявка, история.

### Сценарий 2 — План превентивного ТО (RBAM)
- Приоритет = **вероятность (модель) × последствие (эвристика по типу системы/объекта)**.
- Выход: готовый план «какие каналы/насосы/датчики в какой квартал», оценка эффекта
  («если обслужить топ-100 — снижение X% отказов в окне»).
- Это и есть заявка на **превентивное обслуживание** из ТЗ — но оцифрованная через риск,
  а не через 24ч-алерт.

### Сценарий 3 — Человек в цикле → дообучение
- Диспетчер подтверждает/отклоняет прогноз («ложно/реально») — сервис собирает метки,
  журнал прогнозов, audit.
- Это будущий ground-truth (эксперты: журнал ОДС — HelpDesk без интеграции) и
  единственный честный путь улучшить 24ч-задачи.

### Сценарий 0 (реагирование, оставляем) — «продолжение начавшегося»
- Это то, что реально работает на 24ч: **эхо-подтверждение** (fire:
  «подтверждено задымление ≥2 ИПР → ожидайте продолжения/повтора 24ч», топ-152 prec 0.70);
  **последовательности доступа** (дверь+объёмный+движение, эксперты 0.5); ночь/выходные baseline.
- Легаси-требования ТЗ по алертам закрыть этим сценарием, а не «ранним предсказанием».

### Фаза C — Усиление сигнала на текущих данных (после релиза v0, P1)
1. **Sensor**: пер-типовые модели (дым/КД/газ/движение) — разные физики, разные пороги
   (ML_PLAN §2 подтверждает); стратифицированные метрики.
2. **Fire**: эхо-верификация (пары ИПР в 1–5 мин, окна) как фичи/атрибуты карточки;
   отдельный приоритет «ручной извещатель» vs «подтверждённый дым».
3. **Access**: sequential-фичи (дверь→движение 5–15 мин), night/weekend-baseline,
   объект×день аномалии (z/IF).
4. **Value-пайплайн**: тренды температуры/газа по объекту (7д отклонение) для деградации
   — рекуррентные признаки после стабилизации GBDT.
5. **L2-агрегация**: объектный индекс риска (правила/бустинг поверх L1) для карты.

### Фаза D — Fallback «буква ТЗ» (резерв, готовить заранее, но не в демо-базе)
1. Скрипт `report_tz_compliance.py`: для каждой задачи — P(≤24ч) на holdout,

2. Готовые честные формулировки:
   - wear: порог 24ч достигает Precision 0.7 с Recall ~0.8 (реальное соответствие);
   - fire: топ-152 → Prec 0.70 (Recall 0.35) — «соответствие по прецизии на ограниченном топе»;
   - access/sensor: на 24ч недостижимо — обоснование (база 1% / 0.3%, отсутствие СКУД/ОДС),
     контрпредложение: топ-K по risk30 + медиана дней.
3. Демо-режим «ТЗ-строгий»: если заказчик потребует именно 24ч — включаем эту панель
   с оговорками и не скрываем ограничения (доверие важнее метрики).

### Фаза E — Данные P2 (долг, интерфейсы готовы)
1. Адаптеры read-only: АРМ-Контроль (сварки/допуски), журнал ОДС, СКУД, реестр ремонтов/возраст.
