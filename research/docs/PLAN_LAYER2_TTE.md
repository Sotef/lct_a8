## 0.1. Суть проблемы текущего слоя 2

В `10_wear_series.ipynb` слой «дней до события» — **ор-динальный мультикласс**
по 8 бин-классам (≤0.5д … >30д) с классом «>30д/цензур» как обычным классом.

Концептуальные недостатки:
1. **Не учитывается цензурирование корректно**: строки без будущего события в
   данных кладутся в класс «>30 дней» как наблюдаемые, хотя это right-censoring.
2. **Одна точка** (ожидаемые дни = Σ p(класс)·mid) вместо **распределения S(t)**.
3. Метрика MAE по серединам бинов смещена и не робастна к цензуре.
4. Два слоя (P(события в горизонт) и «дни до») обучаются независимо и не
   согласованы между собой.

Целевое состояние: модель выдаёт **кривую выживаемости S(t)** (для 6ч/12ч/24ч/
48ч/7д/14д/30д), из которой выводятся и P(событие ≤ H), и медиана/ожидаемые дни,
и интервалы — единый слой вместо двух.

## 1. Быстрые выигрыши (низкий риск, ~1–2 дня)

### 1.1. Правильное кодирование цензуры
- Формат разметки: `(время_наблюдения, событие_flag)`.
- Событие: `days = dist_to_event`, `event = 1`.
- Нет будущего события: **административная цензура** на фиксированном горизонте
  (напр. t+30д): `days = 30`, `event = 0`.
- Убирает главное искажение текущего «>30д» класса.
- Библиотеки: `lifelines`, `scikit-survival` (`Surv.from_arrays(event, time)`).

### 1.2. Честные метрики (в дополнение/вместо MAE)
- **C-index / concordance**: `sksurv.metrics.concordance_index_censored` (или
  `lifelines.utils.concordance_index`) — робастна к цензуре.
- **IPCW Brier / integrated Brier**: `sksurv.metrics.brier_score`,
  `integrated_brier_score` — качество распределения.
- **Медиана выживаемости** (`lifelines.utils.median_survival_times`) + интервалы.
- MAE — только справочно, по нецензурированным строкам.

### 1.3. Якорные базовые модели
- **Kaplan-Meier / Nelson-Aalen** по типам каналов (фон риска).
- **lifelines**: `CoxPHFitter`, `WeibullAFTFitter` — интерпретируемый baseline и
  источник «базового hazard» для фич; проверить PH-допущения.

## 2. Основной апгрейд: дискретно-временная hazard-модель (person-time)

Идеально подходит нашим 6-часовым бакетам (аналог pycox `LogisticHazard`/
Nnet-survival, но на CatBoost, без нейросети):

1. Каждую строку (канал, бакет) «раздвинуть» во время → person-time датасет:
   - шаги t = 1..K; метка = 1 в бакете события, 0 на всех предыдущих шагах;
   - после события и за цензурой строки не включаются.
2. Добавить фичи времени: «часов/бакетов до конца горизонта», час, день недели,
   месяц — модель учит **hazard P(событие в шаг t | дожил до t)**.
3. CatBoost логистический → `S(t) = ∏(1 − ĥ)`:
   - `P(событие в 24ч) = 1 − S(24ч)` — **объединяет слой 1 и слой 2**;
   - медиана/ожидаемые дни и интервалы из S(t).

Плюсы: корректная цензура, распределение, переиспользует готовый пайплайн фич и
CatBoost. Минусы: датасет вырастает в ~K раз (K=40 бакетов на 10 дней → ~64 млн
строк): ограничить горизонт 7–14 днями и/или прореживать риск-сеты.

## 3. Готовые survival-модели для сравнения (короткие эксперименты)

| Модель | Как задать цель | Оценка | Примечание |
|---|---|---|---|
| **XGBoost AFT** (`objective='survival:aft'`) | ranged labels `label_lower_bound/upper_bound`; right-censored = `[t, +inf)` | `aft-nloglik`, C-index | только через `xgb.DMatrix` (не sklearn-API); распределения `normal/logistic/extreme` — для наших хвостов лучше `logistic/extreme` |
| **CatBoost `loss_function='Cox'`** | время + флаг цензуры | risk-скоро → перевод через Nelson-Aalen | быстрая альтернатива; риск-скор не даёт сразу дни — нужен baseline hazard |
| **scikit-survival** (`RandomSurvivalForest`, `GradientBoostingSurvivalAnalysis`) | `Surv.from_arrays(event, time)` | `concordance_index_censored`, IPCW-Brier | off-the-shelf, хорош как бенчмарк |
| **lifelines** (CoxPH, WeibullAFT) | `duration, event_observed` | concordance, S(t) | интерпретируемость; PH-проверка |
| **pycox** (PyTorch): `LogisticHazard`, `MTLR`, `DeepHit`, `PC-Hazard`, `DeepSurv` | дискретная сетка времени | `EvalSurv` (C-index, Brier, NLL) | топ по качеству распределения; тяжелее (нейросеть, препроцессинг); «на потом», A/B |

## 4. Фич-инжиниринг для дня-события

- **Горизонт-зависимые признаки**: окна 3/7/14/30д — другие, чем для бинарного
  24ч; отношение «событий за 7д / событий за 30д»; `time_since_last_series_start`;
  длина текущей серии.
- **Эмпирический фон риска**: пер-типовой/пер-объектный сглаженный KM/hazard-профиль
  как фича (учёт гетерогенности каналов, без ручной разметки).
- **Событийные последовательности**: число стартов серий за 1/7/30д, «частые
  старты → ближе следующий», паттерны вкл/выкл насосов (сценарий подтопления).
- **Цифровые датчики** (когда дойдём): тренды значений, flatline, время выше
  порога — критично для дня-события на цифровых типах.

## 5. Калибровка и продукт

- Калибровать S(t): isotonic per time-bin / Platt; проверять IPCW-Brier.
- Продукт: карточка с **кривой выживаемости** (S при 6ч/12ч/24ч/48ч/7д),
  медианой и P(≤H) — решение диспетчера по распределению, а не по точке.

## 6. Валидация

- Walk-forward + **административная цензура** на 30 дней.
- Метрики ТОЛЬКО с учётом цензуры: C-index, IPCW-Brier (+ MAE справочно).
- По типам/объектам отдельно (неравный парк каналов).

## 7. Рекомендуемая последовательность работ

1. **День 1–2**: правильная цензура + KM-якорь + C-index/IPCW-Brier на текущем
   слое → честные цифры вместо MAE.
2. **День 2–4**: **person-time hazard на CatBoost** (главный апгрейд) → S(t),
   P(24ч), медиана; сравнить с текущим ор-динальным слоем.
3. **День 4–5**: XGBoost AFT и CatBoost Cox как независимые бенчмарки; выбор по
   C-index + Brier.
4. **Опционально**: pycox `LogisticHazard`/`MTLR`; фич-апгрейд (фон риска,
   гетерогенность, последовательности).
