## 2. Схема журналов (все 8 лет — идентичные колонки)

```
ид_события, ид_канала_данных, дата, время, тревожное, значение_датчика
```

Особенности:
- **`тревожное`** — флаг (f/t в реальных выгрузках; false/true в примере).
- **`значение_датчика`** — смешанные типы:
  - *числа* `0.00…0.30`, отрицательные — показания температуры/газа/дыма;
  - *текстовые статусы*: «Норма», «Неопределен», «Неисправен», «Обесточен», «Не замкнут», «Включен/Выключен», «Движения нет/Обнаружено движение», «Обнаружен дым», «Обнаружен газ», «Затоплен», «Питание от сети/батарей» и др.
- В **2019–2021** значения чаще текстовые, с **2022** — преобладают числа: изменился формат выгрузки СМВУ (телеметрия вместо событий-статусов).
- Итог по датасету: ~50 тыс. уникальных значений, из них ~48 тыс. текстовых (многие — «мусор»: даты, обрывки).

Почти все топ-15 — **газовые датчики** (60–65 тыс. событий/год на канал) — самые «шумные». Вторые — каналы телеметрии 0.00/0.01 (тысячи событий в день). Это прямое указание для направления «Отказ датчика»: моделировать **паттерны ложных сработок и частоту «шума»**.

## 7. Пространственная структура (тег инженерной системы)

Формат тега `p1-p2.p3.p4.p5.`:
- `p1` — индекс коллектора/объекта (847, 914, 257, 884, 418…),
- `p3` — пикет (ПК) для температурных/тепловых каналов,
- `p5` — номер логического канала (255 = «все», 4095 = «зона»).

Справочник объектов — иерархия `district → controlHouse → guardObject`. Прямой связи «канал → ид_объект» нет, связь опосредованная (через ПК/названия). Для карты объектов нужен парсинг ПК/коллектора из тегов и названий.

## 8. Рекомендация: распаковывать и объединять или нет?

**Факты:**
- Каждый `.7z` — ровно один CSV одного года, схема идентична. Это уже «по годам».
- Полное распакованное — ~15.9 ГБ; в 24 ГБ ОЗУ целиком не помещается.

**Решение:**
1. **Распаковать один раз** в `dataset/extracted/` — сделано (нужно и EDA, и бэкенду).
2. **НЕ объединять в один гигантский CSV/DataFrame.** Вместо этого:
   - EDA — читать по годам чанками (реализовано);
   - ML — строить **пер-канальный датасет**: агрегация событий в окна (час/день) по `ид_канала_данных` → признаки (число событий, доля тревог, «шум», доля неисправных статусов) → целевая «отказ/событие в следующие 24 ч». Получается ~11.5k каналов × дней — живёт в памяти;
   - сохранять паркет по годам в `dataset/parquet/` для быстрого доступа.
3. **«Вес новым данным»** — не перераспаковкой, а стратегией обучения: временной сплит (train ≤ 2024, val = 2025, test = 2026/последние 90 дней) + экспоненциальное взвешивание по свежести. Это соответствует ТЗ (горизонт 24 ч, работа на новых данных).
4. **Баланс классов** — тревог всего 0.2–2.2%; применять class_weight/SMOTE только на train, метрики считать по типам датчиков.

## 9. Дальше (ML Research Roadmap)

1. **Feature pipeline** (`research/features.py`): почасовые/дневные признаки по каналам: count событий, count тревог, «шум» (смены 0.00/0.01), число «Неисправен/Обесточен», скользящие средние (7/30 дн), ПК/объект из тегов.
2. **Целевая переменная**: бинарная «неисправность/аварийное событие канала в следующие 24 ч» (по статусам «Неисправен», «Обесточен», «Не замкнут», «Затоплен» + тревоги дыма/газа). Отдельно — «отказ датчика» по «Неисправен».
3. **Baseline** → LightGBM/CatBoost, временной сплит, Precision≥0.7 / Recall≥0.5, PR-AUC, калибровка.

## 13. Кампании проверок и правило исключения из сплитов

**Проблема:** пик тревог 2021W17–W22 (апрель–май) — 990 тыс. тревог дыма = ~85% всех тревог дыма за 8 лет; в 2021 всего 1.17 млн статусов «Неисправен» у дыма. Это не реальные отказы, а **эффект регуляторики**:

- **ППР №1479** (Правила противопожарного режима) вступили в силу **01.01.2021** (п.2 постановления от 16.09.2020, docs.cntd.ru).
- **С 01.03.2021** — вступили в силу новые СП МЧС по пожарной сигнализации: **СП 484.1311500.2020**, **СП 485**, **СП 486** (приказы МЧС 2020 г.).
- Плюс переходные положения постановления Правительства **№2463 от 31.12.2020**.

После этого в апреле–мае 2021 началась массовая проверка/ремонт дымовых извещателей — отсюда всплеск.

**Решение (реализовано в `data_utils.py`):**
- `CAMPAIGN_WEEKS` — календарь известных кампаний (формат: `(год_неделя_нач, год_неделя_кон, описание)`):
  - `2021W16–W23` — переходный период вокруг пика 2021;
  - `2021W17–W22` — сам пик кампании;
  - `2026W23` — локальный всплеск (помечен как «проверить», исключается по умолчанию).
## 14. Подготовка данных к обучению (ноутбук 07_data_prep)

**Проблема:** аномальные недели кампаний (2021W16–W23, 2026W23) почти целиком
бьют по **дыму** (90.6% всех тревог дыма за 8 лет); остальные типы < 5% (фон).

**Решение — медианная нейтрализация:**
- Строим суточную панель «канал × день» (артефакт `daily_agg_2019_2026_дым.csv`):
  счётчики событий/тревог/неисправностей/шума + ISO-неделя + флаг `аномально`.
- В аномальные дни признаки **заменяются на медиану «чистых» дней канала**
  (типичный фон), чтобы скользящие фичи не впитали всплеск проверки.
- Целевая переменная **цель_24ч**: были ли неисправности у канала в следующие
  24 часа (по исходным, не заменённым данным); аномальные дни → NaN
  (исключаются из обучения, но остаются в панели для непрерывности окон).

**Итоговая панель** `train_panel_дым.csv` (463 881 строка × 23 колонки):
- фичи: события/тревоги/неисправности/шум за 3/7/14/30 дней (rolling),
  z-скор частоты события относительно фона канала;
- цель: `цель_24ч` (4.29% положительных по чистым дням);
- флаг `аномально` для исключения из сплитов.

**Почему медиана, а не NaN/пропуск строк:** скользящие окна не рвутся,
канал не «выбивается» ни в плюс (всплеск проверки), ни в минус (пропадание).
Ограничение: это нейтрализация, а не точная реконструкция; длительные
реальные «выключения» канала надо обрабатывать отдельно (флаг no_data).

**Следующие шаги:** расширить панели на остальные типы (по мере задач),
добавить контекст соседей (2.2), приступить к baseline LGBM для дыма.
- `EXCLUDE_WEEKS_DEFAULT` — множество недель `{202116..202123}`, исключаемых из сплитов.
- `week_is_campaign(week)`, `add_campaign_flags(df)`, `filter_clean_weeks(df)` — утилиты пометки/фильтрации.

**Результат (из ноутбука 06, ячейка 6.5):** средняя неделя кампании = 120.5 тыс. тревог (доля 10.1%) vs 3.6 тыс. (0.53%) у чистых — в 33 раза больше. После исключения остаётся **383 чистых недели из 392**.

**Правило для ML:** перед построением сплитов применять `du.filter_clean_weeks(...)` (или передавать `exclude` в конфиг), чтобы модель не выучила «эффект проверки» вместо поведения датчиков. Это же касается построения целевой метки «отказ датчика»: метки «Неисправен/Обесточен» внутри кампаний не считаются реальными отказами.
