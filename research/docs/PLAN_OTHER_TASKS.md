## 0. Общий принцип

Три задачи решаются **тем же способом, что слой 2 «износ»** (`11_wear_tte`):
6-часовой панель канал×бакет → серии событий → правая цензура →
person-time discrete hazard (CatBoost) → метрики на **holdout ≥ 2025-07-01**
(обучение ≤ 2024-12-31, внутренняя валидация 2025H1). Единый слой выдаёт и
P(событие ≤ 24ч), и кривую S(t)/медиану дней.

Данные: только журнал СМВУ (`ext-journal-*.csv`) + справочники; журналы ОДС,
реестр оборудования и АРМ-Контроль (сварочные работы, допуски) **в датасет не
поставлены** — их эффекты моделируем косвенно (см. §3).

## 2. Результаты web-исследования (17.09.2026)

**Feature engineering (общее для событийных рядов):**
- tsfresh (Christ 2018; tsfresh.readthedocs) — автоматические фичи временных
  рядов: rolling-статистики, автокорреляция, число пиков, FFT, линейный тренд.
  Не подходит для потокового режима и очень нерегулярных рядов — для нас как
  апгрейд на бинарные классификаторы, не для hazard-модели.
- SFFDD (arXiv:2109.09856) — «обогащённые фичи» для предсказания отказов:
  производные преобразования многомерного ряда → признаки отказовых паттернов.
- ForeNet (arXiv:2412.17823) — attention-модель RUL с окном прогноза 2 недели;
  точно предсказывает время отказа (ошибка от 10 мин до ~2 дней).
- Chronos-2 / time-series foundation model embeddings для RUL
  (arXiv:2606.11990) — предобученный эмбеддер + лёгкая голова; сильный базлайн.
- Вейвс-мониторинг (arXiv:2602.16101) — VAE-аномалии + метаданные + GBM-аномалия.

**Соревнования/кейсы Kaggle и др. (паттерны решений):**
- Kaggle «Machine Predictive Maintenance» / Azure PdM — цель «отказ до N дней»;
  решения: rolling windows, time-since-last-failure, feature + GBM/LGBM, F1.
- NASA Turbofan RUL (PHM08/12) — слайдинг-окна, кусочно-линейный RUL, tsfresh
  + GBM/LSTM; метрика RMSE. Наш горизонт = «дни до события», аналог RUL.
- Датчики/детекторы дыма: господствует предсказание **ложных срабатываний** по
  частоте и характеру тревог одного ИПР (NIST; розжиг/перезапуск, dust);
  сложность — высокая неоднородность и сезонные кампании (у нас 2021, 2026W23).
- Доступ/двери: задачи «door open sensor» (классификация открыто/закрыто) и
  adversarial-взломы (WCECS); решения: temporal proximity (открытие двери →
  движение в течение N секунд), time-of-day/weekday baseline, Isolation Forest,
  LSTM-autoencoder, событийные последовательности.

## 3. Фичи (план; переиспользуем панель `features.make_subdaily_panel`)

Базовый слой (уже в панели, как в wear):
- окна 12ч/24ч/48ч/7д/30д по счётчикам событий/тревог/неисправностей/шума;
- z-скор на канал (пересчитывается ТОЛЬКО по обучающему окну);
- сезонность (час бакета, день недели, месяц, день года);
- контекст объекта (все каналы объекта за бакет и окна);
- серийная разметка: события = первое срабатывание серии, длина серии,
  «дней с последнего события/неисправности».

Задача-специфичное:
- **Пожарный риск**: доля шума/ложных срабатываний на дым-канал (значения
  0.00/0.01, повторные сработки), возврат после тревоги (reset pattern),
  тренд температуры по соседним температурным каналам объекта, связь
  «дым+температура» за окно. (АРМ-Контроль — сварки/горячие работы: интеграция
  на будущее, сегодня косвенно через суточную/сезонную сезонность.)
- **Отказ датчика**: паттерны «шума» (частота 0.00/0.01, смена состояния),
  давность последней неисправности/тревоги, бёрст-индикатор (события в 6ч-окнах
  без пауз), история ремонтов → косвенно через частоту статусов «Неисправен».
- **Доступ**: работа/ночь/выходные (baseline по времени суток), «открытие+
  движение» в пределах одного бакета, цепочки последовательных тревог разных
  каналов объекта (дверь→объёмный→движение соседней зоны), частота доступа за
  1/7/30д, число разных каналов, сработавших за окно.

## 4. План реализации (TTE)

1. Общий раннер `research/task_tte.py` (--task fire|sensor|access): сборка
   панели нужного типа → цензура/сплиты (как wear) → discrete hazard →
   метрики + KM-якорь + порог P(24ч) на валидации.
2. **fire**: панель дым+тепло+температура → событие = серия тревог дыма.
3. **sensor**: панель всех датчиков → событие = статус «Неисправен/Обесточен».
4. **access**: панель охранных → событие = серия охранных тревог; добавить
   unsupervised-аномалию по времени суток как вторую модель (сравнение).
5. Сравнение моделей: discrete hazard vs SurvivalAft vs KM-якорь (как в 11/12).

## 5. Ограничения

- ОДС/АРМ-Контроль/реестр ремонтов в датасете отсутствуют → «экспертные»
  признаки (график сварочных работ, допуски) недоступны; эффект будет
  учитываться при получении данных (адаптеры read-only).
- Охранная тревога ≠ доказанный взлом (нет СКУД-логов): модель предсказывает
  «аномальный доступ/сработку», решение принимает диспетчер (по SERVICE_PLAN).

## 8. Аугментация и синтетические данные: решение (18.09.2026)

Факты по real train (≤ 2024-12-31, вне кампаний), проверено по
`tte_subjects_{task}.parquet`:

| Задача | строк train | серия_старт (всего) | событий-серий D≤1д | база цель_24ч |
|---|---|---|---|---|
| fire   | 852k   | 18 273 | 11 077 | 1.30% |
| sensor | 2 978k | 12 812 | 5 198  | 0.17% |
| access | 1 000k | 53 320 | 9 238  | 0.92% |

**Вердикт: классические аугментации/SMOTE/oversampling и «синтетика ради
баланса» НЕ делать.** Причины:

1. **Дефицита данных нет — есть дефицит сигнала.** Для GBDT 5–53 тыс. реальных
   событий достаточно; дисбаланс на обучении уже решается стратифицированной
   выборкой (`n_starts/n_fault/n_nonfault`). Синтетика добавляет объём, а не
   информацию: fire с Uno-C≈0.51 на 18k реальных событий останется ~0.51 и на
   18M синтетических.
2. **Порог Precision≥0.7 на 24ч принципиально не решаем данными:** база 0.17–1.3%,
   PR-AUC 0.008–0.105. Продуктовая постановка уже переключена на «топ-список +
   P(≤7д) + медиана дней» (§0) — она опирается на ранжирование (Uno-C 0.70/0.79),
   которому синтетика не нужна.
3. **Риски специфичны для пайплайна:** синтетический субъект с форсированным
   событием в day N даёт идеально «выучиваемый» паттерн в person-time discrete
   hazard → переобучение на артефакте и падение на реальном holdout; искажение
   hazard/S(t) ломает калибровку (O/E уже смещён 1.5–2); синтез по train-статистикам
   закрепляет реежимы, которые в holdout ≥ 2025-07-01 могут исчезнуть (кампании
   2021W17-23, 2026W23). Любой шаг с валидационными/holdout-статистиками = утечка.

**Исключение (пилот, только для sensor):** механистическая симуляция деградации
(шум 0.00/0.01 → учащение → смена состояния → «Неисправен») — единственная из
трёх задач с правдоподобным физическим механизмом. Не приоритет: реальных
событий уже 12.8k. Протокол A/B — обучение на real+synth vs real-only, оценка
ТОЛЬКО на реальном holdout (Uno-C, PR-AUC, O/E); без ≥10–15% относительного
прироста по зафиксированным метрикам — вариант выбросить и не возвращаться.

Бюджет направляем на: переопределение события fire (объект/«серьёзная тревога»),
value-пайплайн температуры, noise-паттерны ИПР, sequential-фичи access,
калибровку + операционную точку «топ-K + ожидаемое число». Настоящие сигналы
дадут данные ОДС/АРМ-Контроль/реестра, а не синтетика.

## 9. Итерация 3: переопределение события fire + семантические фичи (18.09.2026)

Реализовано (пайплайн `features.py` + `rebuild_task_panels.py`):

1. `features.make_subdaily_panel` расширен параметром `extra_cols`: счётчики
   «по типу канала» (`alarm_by_type`) и «по значению журнала»
   (`value_by_type`); объектный счётчик числа активных каналов
   (`каналов_<name>_об_б`) — подтверждение на объекте. Маски строятся по
   **id-множествам каналов из реестра** (а не по строкам типов) — это убрало
   баг совпадения строк при агрегации.
2. Событие fire переопределено: **«серьёзная тревога»** =
   подтверждённое задымление (≥2 дымовых каналов объекта за 6ч бакет,
   `задым_подтв_об_б`) ИЛИ срабатывание ручного извещателя
   («Рычаг сдернут», значение журнала, не флаг тревожное).
3. access: добавлены `тревог_дверь`/`тревог_движение` и sequential-признак
   `дверь_движение_об_б` (дверь+объёмник в одном бакете).
4. sensor: спроектированы `пр_разрывов` («Не замкнут») и `неисправн_дым`
   (частично — сборка панели ~1.5–2 ч, отложена; старые шум-фичи остаются).

| access | новая панель (+дверь/движение) | 0.788 | 0.822 | 0.055 | **0.067** | 1.0% |

Выводы:

- **Скачок fire объясняется переопределением события, а не фичами**: A/B на
  новой панели со старым событием даёт лишь 0.507→0.538. «Серьёзная тревога»
  отделяет сигнал (подтверждённый дым / ручной ИПР) от спорадических ложных
  тревог → Uno-C 0.87, PR-AUC(24ч) 0.40 (была 0.08). Значение «Рычаг сдернут»
  НЕ равно флагу `тревожное` (часть значений d{тревожное='f') — фиксируется
  только по значению журнала.
- Задымления записываются в журнал существенно чаще, чем тревожные флаги
  («Обнаружен дым» ~56 тыс. строк/год при ~2.4 тыс. `тревожное='t'`) —
  подтверждение по значениям, а не флагам, — ключевое.
- access: sequential-признак «дверь+движение» повышает PR-AUC 24ч на ~20%
  относит.; ранжирование уже было сильным.
- Калибровка осталась смещённой в средних децилях (O/E до 1.5–2) — следующий
  шаг isotonic per-bin + операционная точка «топ-K + ожидаемое число».
- Требуются value-пайплайн температуры и шум-паттерны ИПР для fire
  (следующая итерация); sensor-новые колонки ждём с пересборкой панели.

Про LSTM — отдельный вывод в §10.

## 10. Нужна ли LSTM/GRU? Решение (18.09.2026)

**Вердикт: НЕТ, в текущей итерации LSTM не нужна; как бенчмарк — позже и
только GRU/Transformer-discrete-hazard на равном сплите.**

Аргументы:

1. **Бутылочное горлышко — определение события и признаки, а не класс модели.**
   Один и тот же CatBoost-TTE: на «сырых тревогах» fire → Uno-C 0.51, на
   «серьёзной тревоге» → 0.87 (§9). Никакая более выразительная архитектура
   не дала бы такого скачка без смены разметки.
2. **Формат данных не тот, для которого LSTM сильна.** LSTM выигрывает на
   плотных сырых последовательностях (значения датчиков в каждый шаг). У нас —
   разреженные 6ч-счётчики событий (buckets), причём временная динамика уже
   решена rolling-окнами: GBDT с window-признаками ≈ вручную выбранные лаги. Для
   нашей задачи GBDT стабильно выигрывает у NN на таблицах без гигантских
   объёмов и без «сырых» сигналов.
3. **Риски > выгоды для редких событий:** малый батч положительных (5–53k
   событий в train), сильный дисбаланс, нужна пуританская временная валидация
   (train/holdout без утечек — у нас жёсткий контракт §tte_pipeline).
   LSTM на таких данных легко переобучается на шум серий.
4. **Что делать вместо этого:** (а) value-пайплайн температуры (сырой сигнал —
   вот где LSTM/автоэнкодер позже имеет смысл на трендах), (б) шум-паттерны
   ИПР, (в) калибровка. После стабилизации GBDT — прогнать GRU-discrete-hazard
   как бенчмарк на том же сплите и сравнить Uno-C/PR-AUC; решение по нему —
   только при выигрыше ≥2-3 п.п. и при воспроизводимом пайплайне.

Практика: в научной литературе подходы RUL/отказы (ForeNet, SFFDD, arXiv)
используют seq2seq/attention там, где есть РЕАЛЬНЫЙ сенсорный ряд (температура,
токи) на каждом шаге. У нас такие данные есть только для «Датчика температуры»
(числовые значения 12–24°C) — это (а) ждёт value-пайплайна; (б) естественный
кандидат на рекуррентные признаки/аномалии в следующей итерации, НЕ сейчас.

train ≤ 2024-12-31). Сравнение на одном holdout ≥ 2025-07-01 (20k субъектов,
событие «серьёзных»):

| конфиг | Uno-C | meanAUC | IBS | PR-AUC(24ч) |
|---|---|---|---|---|
| без t-фич (baseline) | **0.869** | 0.875 | 0.048 | **0.404** |
| t-умеренный (8 колонок) | 0.847 | 0.854 | 0.050 | 0.366 |
| t-полный (23 колонки) | 0.819 | 0.830 | 0.055 | 0.327 |

**Вывод: температурные признаки в ТАКОМ виде вредят fire-модели**, а не

- покрытие ничтожно: термодатчики есть только на 30 объектах; 75.5% непустых

как кандидата для sensor-деградации (плотные ряды по каналу) и для
аппер-левел аномалий; в fire — только если появится другой способ признаков
(например, тренд температуры у самого объекта за несколько дней вместо
текущего бакета), что требует отдельного эксперимента.
