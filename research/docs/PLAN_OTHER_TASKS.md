## 0. Общий принцип

Те же шаги, что и слой 2 «износ» (nb 11): 6ч-панель «канал × бакет» → серии событий →
правая цензура → person-time discrete hazard (CatBoost) → метрики на **holdout ≥ 2025-07-01**
(обучение ≤ 2024-12-31, val 2025H1). Внешние источники (ОДС, АРМ-Контроль, СКУД, реестр)
**в датасет не поставлены** — их эффект моделируется косвенно либо отложен (адаптеры read-only, P2).

## 2. Хронология экспериментов и решений (дайджест)

**17.09 · web-ресёрч (§§2).** Ориентиры: tsfresh, SFFDD, ForeNet (attention-RUL), Chronos-2,
Kaggle PDM/NASA RUL; в литературе по дыму доминирует прогноз **ложных** сработок (NIST).
Признаки — rolling-окна, time-since-last-event + GBDT.

**17.09 · первые TTE-прототипы (§6).** Уже равняли: sensor Uno-C 0.698 / PR24 0.012;
fire 0.507 / 0.080; access 0.786 / 0.055. 24ч-порог Precision≥0.7 недостижим → ставка на
«топ-список + P(≤7д) + медиана дней».

**17.09 · ноутбук-10 и проверки (§7).** Бинарный классификатор 24ч сопоставим с TTE-P(24ч) и
тоже слаб (редкие события). Событие во всех задачах = **первое срабатывание серии** (фактор
серий access 4.8×). IsolationForest/z по «объект×день» для fire слабы (recall ~0.06).
`verify_inference.py`: train/inference консистентны (фичи 64==64, z по train-статам, S(t)
монотонна, пересечение (канал,бакет)=0).

**18.09 · аугментация/синтетика отклонены (§8).** Дефицит не данных, а сигнала: 5–53k реальных
событий для GBDT достаточно; синтетика добавляет объём, не информацию. Исключение — только
механистический пилот для sensor, A/B на реальном holdout; без ≥10–15% прироста — выбросить.

**18.09 · переопределение fire (§9) — ключевой прорыв.** `make_subdaily_panel(extra_cols=...)`:
счётчики «по типу канала/значению», объектные `каналов_*_об_б`, маски по id-множествам из реестра.
Событие = «серьёзная тревога». Итог holdout:

| конфиг | Uno-C | IBS | PR-AUC(24ч) |
|---|---|---|---|
| старая панель | 0.507 | 0.084 | 0.080 |
| новая панель, старое событие `тревог` | 0.538 | 0.079 | 0.058 |
| **новая панель, событие `серьёзных`** | **0.869** | 0.048 | **0.404** |

Скачок объясняется **сменой разметки**, а не фичами. access +дверь/движение: PR24 0.055→0.067.

**18.09 · LSTM не нужна (§10).** Бутылочное горлышко — определение события и признаки, а не
класс модели (тот же CatBoost: 0.51→0.87 от смены таргета). Данные разреженные (6ч-счётчики),
GBDT сильнее. Рекуррентное — только позже на плотных value-рядах «Датчик температуры».

**18.09 · value-пайплайн температуры — ОТРИЦАТЕЛЬНЫЙ (§§11–13).** 1.06M показаний, валидных в
[−20,+60] 98.2%, мода 15–23°C, суточный/сезонный циклы есть. Но t-фичи **вредят** fire:
baseline PR24 0.404 → t-чистые(8) 0.366 → t-полные(23) 0.327 → грязные 0.315. Важность t-фич
3.5/100. Причина: покрытие мало (30 объектов), телеметрия разрежена. t-фичи в fire не включаем.

**19.09 · Optuna + t-аномалия (§§14–15).** Optuna-пресет (`optuna_fire_best.json`)
600/0.0091/10/1.22 дал +0.018 PR24 на val, но на полном протоколе хуже дефолта. t-аномалия-фича
на 5 сидах: **0 из 5 улучшений** (Δ Uno-C −0.026, Δ PR24 −0.030) → **отклонена**. Приняты
**дефолты 1000/0.03/10** (`task_tte`, `tte_experiments.fit_discrete_hazard`), флаг `--task-type CPU|GPU`.

**19.09 · калибровка и топ-K (§16).** P(24ч) калибровать бессмысленно; калибруем risk30 (P≤30д).
Топ-K (событий в holdout: fire 306 / access 202 / sensor 61): fire prec@50=1.00, prec@100=0.97,
K=152 при prec 0.70 (recall 0.35); access/sensor 24ч-прецизия недостижима → топ-K по risk30/exp_days.

**19.09 · окно fire 30м / 6ч / 24ч (§17).** 30 мин рвёт задымление (PR24 0.12, Uno-C 0.70),
24ч склеивает инциденты (0.196/0.637). **6ч — оптимум** (0.421/0.792). Полный sweep 1..23ч
(§13/§17, `fire_window_sweep*.csv`): ни одно окно не лучше 6ч-колонки §9 — важнее способ
построения таргета, чем величина окна.

**19.09 · sensor-подтипы ОТКЛОНЕНЫ (§18).** Доминирует «Неисправен» (5024/5198 серий);
«Обесточен» — единицы. Подтиповые таргеты сигнала не дают → обобщённый статус остаётся
правильной постановкой; подтиповые агрегаты сохранены как фичи.

**19.09 · калибровка risk30 per-bin (§19).** ECE: access 0.021→0.016 (применяем `calib30_access.pkl`);
fire 0.078→0.326 (**не применять**, raw); sensor — см. §4. Контракт: `p24` всегда raw; `risk30`
калибруется только у access.

**19.09 · дорожная карта P0/P1/P2 (§20).** P0: пересборка sensor-панели, inference-контракт,
фикс fire-события. P1: drift, per-type модели, горизонт 90д. P2: ОДС/АРМ-Контроль/СКУД/реестр.

## 6. Ограничения (итог)

1. 24ч-раннее предупреждение «первого события» для fire/access/sensor в чистом виде **не работает**
   (PR-AUC 0.03) — фундаментально: редкие события + нет ОДС/АРМ-Контроль/СКУД.
2. GPU vs CPU даёт ±0.02 PR-AUC — device фиксировать в отчётах.
3. Продуктовая ставка (§0/§16): fire — топ-K по p24 (K=152 → prec 0.70); access — топ-K по
   калиброванному risk30; sensor — топ-K по raw risk30 + медиана дней; wear — топ-K по p24/risk30.
