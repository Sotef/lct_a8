Принцип: соединения read-only через отдельные «адаптеры», без переноса ML-логики
в API; feature pipeline уже заложен под joins (`research/docs/DATA_MATRIX.md`).
При поступлении источника достаточно наполнить адаптер — переобучение не требуется,
обновляется только инференс-контракт и отчёты.

## Интерфейс адаптера (схема)

Каждый адаптер — класс с методом `load(entity_key, since=None) -> pandas.DataFrame`:

```python
class ReadOnlyAdapter:
    name: str                       # "arm_control" | "ods_journal" | "skud" | "assets"
    primary_key: str                # ключ соединения
    columns: list[str]              # публичная схема (нормализованные имена)

    def load(self, since=None) -> pd.DataFrame:
        """Возвращает данные только на чтение (кэш/паркет в dataset/_external/)."""
        ...
```

## Таблица источников и их назначение

| Адаптер | P2-источник (жду от заказчика/экспертов) | Ключ join | Что даёт задачам |
|---|---|---|---|
| `arm_control` | Реестр допусков и заявок на работы (АРМ-Контроль: организация, даты, ФИО, тип работ) | ид_объект + интервал дат работ | **fire**: корреляция «сварочные/горячие работы → дым/тепло» (главный триггер по ТЗ, эксперты 16.09); **access**: очистка таргета от плановых работников |
| `ods_journal` | Журнал ОДС (HelpDesk: заявки, реальные/ложные события) | ид_канала_данных/объект → заявка | **sensor**: ground-truth отказа; **fire/access**: верификация событий (метки) |
| `skud` | Проходы/допуски (СКУД) | ид_объект + время | **access**: отличать реальное проникновение от теста/обслуживания; положительная эвристика «нет допуска + дверь+движение» |
| `assets` | Реестр оборудования ОЭ: возраст, истории ремонтов, назначение, вентшахты/насосы/люки | ид_канала_данных / ид_объект | **wear**: возраст + наработка + история ремонтов → плановый отказ; **sensor**: «дней до отказа после ремонта»; severity-маппинг из эвристики → данные |
| `maintenance_plan` | Планы пикетов / ТО-ППР (нормативные сроки) | ид_объект/система | синхронизация RBAM-плана с регламентом |

## Правила подключения

1. Данные кладём в `dataset/_external/<name>/*.parquet` (кэш), источник — read-only.
2. Join на панель строго по act of «прошлое + текущее» (без future leakage).
3. Новые колонки добавляются как extra_cols (см. `features.py`) и пересобирают
   панель без изменения логики (idempotent-сбоку уже есть в `rebuild_task_panels`).
4. Ground-truth через подтверждения диспетчера (`POST /forecasts/{id}/decision`)
   накапливается в журнале прогнозов — важнейший «адаптер» обратной петли.

## Чек-лист при получении данных
- [ ] `ODS_journal`: разбираемость ключей «событие → заявка» (эксперты: только после восстановления);
- [ ] `assets`: возраст ≠ состояние, нормативный срок ≠ метка износа (не использовать как pseudo-метку);
- [ ] все адаптеры: контроль свежести (дата выгрузки), мониторинг объёма, глубина истории.
