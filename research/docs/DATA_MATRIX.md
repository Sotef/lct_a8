# Матрица «задача → данные → связи»

Версия 0.1 · Для каждой из 4 задач прогнозирования: какие данные нужны,
какие поля связывают источники, что уже есть / чего не хватает.

## 0. Базовые единицы и ключи

| Сущность | Источник | Ключ |
|---|---|---|
| Событие журнала | `ext-journal-{год}.csv` / live журнал | `ид_события`, `ид_канала_данных`, `дата+время`, `тревожное`, `значение_датчика` |
| Канал данных | `справочник_каналов_датчиков.csv` | `ид_канала_данных` (PK) |
| Тип канала | `справочник` (`тип_датчика`, `тип_инж_системы`) + Прил.1 (`ИД типа канала`) | `тип_датчика` |
| Локация канала | `тег_инженерной_системы` → `channel_tag_parsed` (`p1..p5`) | `ид_канала_данных` → `p1` (коллектор), `p3` (пикет) |
| Объект диспетчера | `справочник_объектов_диспетчер.csv` | `ид_объект`, иерархия `родитель→ребёнок` |
| Известные кампании | константа в `data_utils.CAMPAIGN_WEEKS` | `год_неделя` |

**⚠ Обновлено по итогам встречи 16.09:** связь `канал → ид_объект` **восстановлена** —
обновлённый справочник каналов содержит `ид_объект` (0 NaN из 11 485). Старый
составной `тег_инженерной_системы` (`p1..p5`), возникший при обезличивании,
в решении не нужен. Гео-координаты не обязательны: карта — схематичная линейная
(коллектор → пикеты `p3`, шаг 10 м, для демо можно другой шаг), МСК — при желании.

### Типовые joins (общие для задач)

```
журнал ──ид_канала_данных──▶ справочник_каналов ──тег──▶ channel_tag_parsed (p1,p3)
справочник_каналов ──тип_датчика──▶ словарь типов (smoke/gas/...)
channel_tag_parsed.p1 ──(агрегация)──▶ «объект» для контекста соседей
справочник_объектов ──ид_объект/родитель──▶ иерархия (для дашборда/карты)
```

## 1. «Отказ датчика»

**Цель:** предсказать деградацию/выход из строя датчика (контактные, объёмные, температурные, дымовые, газовые) по паттернам ложных сработок, шуму и истории ремонтов.

### Данные и связи

| Данные | Связь с остальными | Статус |
|---|---|---|
---

## 2. «Пожарный риск»

**Цель:** раннее предупреждение о повышенном риске пожара/задымления по динамике температурных и дымовых датчиков + корреляция со сварочными/горячими работами.

### Данные и связи

| Данные | Связь | Статус |
|---|---|---|
| Журналы (температура, дым, газ) | `тип_датчика` in {temperature, smoke, gas} | ✅ есть |
| Динамика показаний | численные `значение_датчика` (температура) + флаг тревог | ✅ есть |
| **Графики сварочных/горячих работ (АРМ-Контроль)** | должны связываться по **объекту/ПК/дате** с каналами | ❌ нет — ключевой недостающий источник |
| Дерево объектов | `p1`/`p3` ↔ объект (нужен маппинг) | ⚠ косвенно |
| Погода/сезон | дата → внешний источник | ⚠ нет (внешний) |

### Ключевые связи

```
события дыма/тепла ──канал──▶ p1 (коллектор) ──▶ соседние пикеты (p3) — контекст «задымление рядом»
арм_контроль.заявка ──объект/дата────▶ каналы того же объекта — «идут горячие работы»
```

### Фичи
- рост температуры (тренд, экстремумы) за окно;
- сработки дыма/газа рядом (context фичи из 2.2);
- **флаг «горячие работы на объекте сейчас/недавно»** (по данным АРМ) — без этого
  задача недо-обеспечена факторами-триггерами.

## 3. «Несанкционированный доступ»

**Цель:** аномальные паттерны доступа, прогноз попыток проникновения по контактным/объёмным датчикам, СКУД и журналам допусков.

### Данные и связи

| Данные | Связь | Статус |
|---|---|---|
| КД Дверь/АВ/Люк, датчики движения | `тип_датчика` in {contact, movement}; `p3` → пикет | ✅ есть |
| Журналы допусков (АРМ-Контроль) | по объекту/дате — «легальный заход» → разделение норм/аномалий | ❌ нет — попросить |
---

## 4. «Износ инфраструктуры»

**Цель:** прогноз необходимости ремонта конструкций, вентшахт, насосов, люков по обследованиям ОЭ, возрасту оборудования, интенсивности эксплуатации, внешним факторам.

### Данные и связи

| Данные | Связь | Статус |
|---|---|---|
| Насосы/вентиляторы/фаза (состояние, неисправности) | `тип_датчика` in {pump, fan, phase} | ✅ есть |
| **Визуальные обследования ОЭ** | по объекту/зоне → фактическая потребность ремонта | ❌ нет — попросить |
| **Возраст оборудования** (реестр ОЭ, даты ввода) | канал/объект → возраст → износ | ❌ нет — попросить |
| **Интенсивность эксплуатации** | из журналов: число включений/наработка | ✅ частично (насосы/вентиляторы) |
| Погода/сезон | объект/дата → внешние факторы | ⚠ нет (внешний) |
| Люки (КД Люк), вентшахты | `тип_датчика` = КД Люк + теги `p1/p3` | ⚠ частично |

### Связи

```
насос ──канал──▶ p1 ──▶ объект ──▶ возраст, климат, отчёты обследований ОЭ
("наработка" насоса) ──▶ интенсивность эксплуатации
```

### Фичи
- **наработка** (count включений, суммарные мотор-часы по журналу);
- возраст парка (когда появятся даты ввода); частота «Обесточен/Затоплен»;
- внешние: мороз/жара/осадки (внешний источник; иначе — сезонный признак);
- **выходная метка** при наличии обследований ОЭ: «категория состояния → ремонт нужно
  выполнить в горизонте».

| Графики сварочных/горячих работ (АРМ-Контроль) | Пожарный риск | объект (`ид_объект`), дата | ❌ нет — ключевой триггер пожара |
| Журнал допусков / заявки (АРМ-Контроль) | Несанкц. доступ | объект, дата, ФИО/организация | ❌ нет — без него supervised по доступу не строится |

| Визуальные обследования ОЭ | Износ | объект/зона, дата | ❌ формальный источник не подтверждён |
| Планы пикетов / график ТО-ППР | все (исключение плановых работ) | объект, дата | ❌ нет (будущие журналы дефектов/испытаний/отключений/ремонтов) |

**Рекомендация после 16.09:** ключ `ид_канала_данных / тег → ид_объект` уже есть
(обновлённый справочник); приоритет — получить АРМ-Контроль (допуски, графики
горячих работ) и накапливать подтверждения диспетчера в самом сервисе.
| СКУД-события | по объекту/времени — подтверждение физического захода | ❌ нет — попросить |
| Расписание (рабочие часы объекта) | время суток × объект | ⚠ производное |

### Связи

```
КД датчик ──канал──▶ p1/p3 ──▶ маршрут (движение соседних ПК по времени)
допуск(АРМ) ──объект/дата──▶ объект ──▶ какие КД/движения «ожидаемы» в это время
```

### Фичи
- событие КД/движения в нерабочее время;
- **последовательность**: движение в ПК-A → через 2 мин КД в ПК-B (маршрут);
- **отсутствие допуска**: `(КД событие) И (нет записи допуска в +/− 1ч по объекту)` — цель;
- аномалии времени (ночь, праздник, кампании-исключения).
| Журналы СМВУ | `ид_канала_данных` → справочник каналов | ✅ есть |
| Справочник каналов | `ид_канала_данных` PK; `тип_датчика` → выбор субмодели | ✅ есть |
| Теги (`channel_tag_parsed`) | `p1` → коллектор для локальной субмодели; `p3` → пикет | ✅ есть (мы построили) |
| Статусные значения («Неисправен», «Обесточен») | из `значение_датчика` журнала — **целевая метка** | ✅ есть |
| История ремонтов / журнал неисправностей ОДС | по `ид_канала_данных` + дате → **истинные метки ремонта** | ⚠ нет — попросить |
| Возраст датчика (реестр оборудования ОЭ) | по каналу → деградация со временем | ⚠ нет — попросить |

### Фичи (ключевые)
- **Шум**: доля значений «0.00/0.01», частота смен состояния, «тишина» (перерывы);
- **Ложные сработки**: `тревожное=t` без подтверждённого ремонта, повторные срабатывания за окно;
- **Статусы неисправности**: count «Неисправен/Обесточен» за 1/7/30 дней (мишень);
- **Тренды**: наклон частоты событий/шума относительно фона канала.
