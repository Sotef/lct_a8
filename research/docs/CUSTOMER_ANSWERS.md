## 1. «Тревожное» как тревожное сообщение; проверка перед классификацией

**Ответ.** Запись с `тревожное = true` диспетчеры называют **«тревожное сообщение»**.
Диспетчер и дежурный инженер всегда проводят дополнительную проверку, прежде чем отнести
событие к инцидентам, профилактическим работам или ошибкам.

| | Что учтено |
|---|---|
| Уже верно | Поле журнала `тревожное` читается как есть (`app/adapters/journal.py`), «код отказа» не выдумываем; сервис **не** считает тревожное сообщение инцидентом автоматически — решение принимает человек (`/forecasts/{id}/decision`: подтвердить / отклонить / профилактика) |
| Полезно | Терминология решений приведена к словам заказчика: «Подтвердить (инцидент: проверка подтвердила тревожное сообщение)», «Отклонить (ошибка/ложное)», «Профилактика (ППР: планово-предупредительные работы)» — `app/web/js/card_forecast.js` |
| Осталось | Столбец «Тип события» («Предупреждение»/«Норма») из формы Приложения 2 в наших выгрузках отсутствует (есть только флаг) — маппинг добавим при появлении источника, сейчас **не выдумываем** |

## 2. Аварии vs инциденты; охранные сработки и маршрут нарушителя

**Ответ.** Авария = угроза жизни человека; группы: **пожар, наводнение, газ, террор,
аномальная температура**. Сработки охранной системы (люк, аварийный выход, дверь, движение)
— тоже авария, категория **«террор, проникновение нарушителя»**, поэтому **по сработкам
рисуется маршрут движения нарушителя**. «Потеря всей связи» / «потеря всего электроснабжения»
— **инциденты**, не аварии, но «слепота систем» косвенно допускает аварию.

| | Что учтено |
|---|---|
| Уже верно | Охранные типы **уже были в модели** (`access`: КД Дверь, КД Люк, КД АВ, 9-секционный люк, Датчик движения, Стекло — `app/task_cfg.py`) и в весах последствий (`research/inference_contract.SEVERITY_BY_TYPE`: ручной извещатель 0.95, дым 0.85, газ/насос 0.80, затопление 0.75, люк 0.70, дверь/АВ/стекло 0.60, движение 0.55) — **добавлять охранные события не потребовалось** |
| Полезно (сделано) | 1) `app/services/alarm_service.py`: классы `авария` (пожар/наводнение/газ/террор/аном. температура) и `инцидент` (электроснабжение, связь) + флаг `косвенно_авария`; 2) класс виден в карточке прогноза бейджем (`класс_события`, `группа_события`, `охранный`); 3) **новая ручка `GET /objects/{id}/security-route`** — «маршрут движения нарушителя»: упорядоченная по сим-времени цепочка сработок охранных каналов объекта, блок в карточке объекта; 4) `GET /objects/{id}/alarm-classes` — справочник классов |
| Осталось | Маршрут — по 6-часовым бакетам (в сервисной БД агрегаты, не сырые события); при подключении журнала ОДС/СКУД шаг станет минутным. Гео-координаты пикетов не подтверждены → «маршрут» это цепочка точек. ML-признак «слепые зоны» (питание/связь) — в бэклоге |

## 3. Расшифровка обозначений в названиях каналов

**Ответ.** Расшифровка верна: РО/АО — рабочее и аварийное освещение (СП 265.1325800.2016),
ФРО/ФАО — их фидеры, ГРО — группа рабочего освещения, ФВ — фидер вентиляции, В23 — вентилятор,
ФАНС — фидер автоматической насосной станции, ОЗК — огнезадерживающий клапан, ЩАП — щит
аварийного питания с АВР, «Межсекционный» — секционный автомат между вводами.
**ФТС — фидер теплосети, ПУИ — пульт управления индикацией.**

| | Что учтено |
|---|---|
| Уже верно | Эти аббревиатуры в коде **не парсились и не переводились** (работаем с `тип_датчика`/`тег_инж_системы` как с непрозрачными идентификаторами); поиск по репозиторию подтвердил, что ФТС/ПУИ/ОЗК/ЩАП/ФАНС нигде не «расшифрованы» неверно |
| Полезно | Расшифровка зафиксирована в «Глоссарии» ниже — для интерфейса диспетчера и будущих правил по инженерным системам; добавлены ранее неизвестные ФТС и ПУИ |
| Осталось | Правила «важность типа канала в инженерной системе» не выводятся — нет состава систем из РТЭКК |

## 4. Скобки в названиях, «ПК», шаг пикета

**Ответ.** В «ФВ2 (В23)» и «ФРО1 (ГРО1-6)» в скобках — **что питает фидер**; «ПК» в названии
фидера — тоже про то, **что питает фидер** (место щита), а **от чего запитан сам фидер —
в данных нет**. Шаг «один пикет — 10 м» **может отличаться, но в очень редких случаях**.

| | Что учтено |
|---|---|
| Уже верно | Пикеты в сервисе — **логические узлы** (тег `p3`), без пересчёта метров: допущение «10 м» нигде не зашито в расчёты (`object_service.graph_data`, `view_graph.js`); в документации шаг был помечен как «для демо допустим другой» (`SERVICE_PLAN.md`) |
| Полезно | Явно зафиксировано: «ПК = что питает фидер, источник питания самого фидера неизвестен», «шаг пикета может отличаться» — чтобы на 10 м не строили метрики |
| Осталось | Координатная линия коллектора с реальным шагом — после передачи геометрии/реестра пикетов; схема остаётся логической |

## 5. Серии сработок — ППР, а не «плановая проверка»

**Ответ.** Это **ППР — планово-предупредительные работы**; ТО — техническое обслуживание.
Состав инженерных систем — в **РТЭКК**.

| | Что учтено |
|---|---|
| Уже верно | Кампанийные недели **не подмешиваются в метки**: массовые сработки помечаются признаком `аномально` и исключаются из обучения/нумерации; графики ТО/ППР заказчика уже разбираются (`research/planned_work.py` — ППР АКМ, поверка метановых датчиков, `источник = ППР_АКМ`) |
| Полезно | Терминология приведена к заказчику: «Профилактика» подписана как «ППР: планово-предупредительные работы»; в докладе фиксируем «плановая проверка» = ППР, состав систем — по РТЭКК |
| Осталось | Полный состав инженерных систем из РТЭКК не передан; привяжем каналы к системам, когда появится |

## 6. Что устраняют по «Неисправен»

**Ответ.** Перечня «автомат, кабель, контактор, модуль связи, питание шкафа» **достаточно**;
причина может быть и у ресурсоснабжающей организации, и в земле.

| | Что учтено |
|---|---|
| Уже верно | При закрытии заявка **требует комментарий** о выполненных работах — фактическая причина в истории есть |
| Полезно | В карточке заявки добавлен справочник «что устранено» (автомат, кабель, контактор, модуль связи, питание шкафа, прочее): выбранное значение добавляется к комментарию (`устранено: <причина>`), попадает в историю заявки и аудит → годится как метка для дообучения |
| Осталось | Согласовать формулировки «РСО» и «повреждение в земле» (в подсказке UI уже отражено, что причина бывает вне коллектора) |

## Терминология для интерфейса (единая)

* **тревожное сообщение** — запись журнала с `тревожное = true` (не «авария» и не «инцидент»);
* **авария** — угроза жизни человека: пожар, наводнение, газ, террор (проникновение), аномальная
  температура;
* **инцидент** — потеря связи / электроснабжения («слепые зоны»); сам по себе не авария, но
  косвенно допускает её;
* **ППР** — планово-предупредительные работы (в т.ч. серии сработок при проверке),
  **ТО** — техническое обслуживание; состав систем — по РТЭКК.
