# План: ядро MVP в канве индустриальных стандартов (CBM / RBAM / RUL)

Версия: 0.1 · Дата: 20.09.2026 · Автор: ML Research + Product

## 0. Резюме (зачем этот план)

Измерения на 7.5 годах СМВУ (holdout ≥ 2025-07-01) показали:

- **24-часовое «раннее предупреждение ПЕРВОГО события» на чистых строках не работает**
  для fire (PR-AUC 0.03), sensor (0.012), access (0.03): события редкие (база 0.3–1.5%),
  нет журналов ОДС/АРМ-Контроль/СКУД;
- при этом **ранжирование и распределения времени сильны**: Uno-C 0.72–0.79,
  risk30 хорошо калиброван (wear/fire), exp_days (медиана дней) работает;
- эксперты (16.09) смягчили ТЗ: горизонт 24ч — «дефолт, не абсолют», Precision 0.7/Recall 0.5 —
  «стартовые, не жёсткие», оценка экспертная (упаковка > сухих метрик);
- мировая и РФ-практика (Siemens ResilOps/PlantSight, Thames Water+Samotics
  condition-based monitoring, RBAM-обзор Springer, «Цифровой водоканал»,
  NIST по ложным тревогам) действует так же: **состояние → риск → приоритет → план**,
  а не «час отказа».

**Решение:** ядро MVP переформулируем вокруг «приоритизации и планирования
профилактики» (CBM + RBAM + RUL). Исходные критерии ТЗ не выбрасываем —
они переводятся в **резервный (fallback) сценарий** «буква ТЗ» и демонстрируются
там, где сигнал реально есть (wear, fire топ-K), на случай, если заказчик
настоит на прежней постановке.

## 1. Ядро MVP (новое)

**Одна фраза:** сервис отвечает не «что сломается через 24 часа?», а
**«где риск прямо сейчас и что делать в ближайший план ТО?»**.

### Сценарий 1 — Риск-карта (view)
- Топ-риски по объектам/каналам: риск30, медиана дней (exp_days), уровень риска,
  факторы («почему») — топ-фичи + сезон/календарь.
- Карточка прогноза: S(t) кривая (RUL-распределение), P(≤24ч) как вторичная цифра с пометкой
  «низкая различимость первого события», рекомендуемое действие, превентивная заявка, история.

### Сценарий 2 — План превентивного ТО (RBAM)
- Приоритет = **вероятность (модель) × последствие (эвристика по типу системы/объекта)**.
- Выход: готовый план «какие каналы/насосы/датчики в какой квартал», оценка эффекта
  («если обслужить топ-100 — снижение X% отказов в окне»).
- Это и есть заявка на **превентивное обслуживание** из ТЗ — но оцифрованная через риск,
  а не через 24ч-алерт.

### Сценарий 3 — Человек в цикле → дообучение
- Диспетчер подтверждает/отклоняет прогноз («ложно/реально») — сервис собирает метки,
  журнал прогнозов, audit.
- Это будущий ground-truth (эксперты: журнал ОДС — HelpDesk без интеграции) и
  единственный честный путь улучшить 24ч-задачи.

### Сценарий 0 (реагирование, оставляем) — «продолжение начавшегося»
- Это то, что реально работает на 24ч: **эхо-подтверждение** (fire:
  «подтверждено задымление ≥2 ИПР → ожидайте продолжения/повтора 24ч», топ-152 prec 0.70);
  **последовательности доступа** (дверь+объёмный+движение, эксперты 0.5); ночь/выходные baseline.
- Легаси-требования ТЗ по алертам закрыть этим сценарием, а не «ранним предсказанием».

## 2. Требования ТЗ: что куда (не выкидываем)

| ТЗ-критерий | В ядре (как) | Fallback (буква ТЗ) | Примечание |
|---|---|---|---|
| Горизонт ≥ 24ч, прогноз события | risk30 + exp_days + S(t) (RUL-распределения) | P(≤24ч) панель у всех задач с честными PR/прецизией | 24ч-прогноз первого события достижим только на активных строках/для wear |
| Precision ≥ 0.7 / Recall ≥ 0.5 | Precision@топ-K, ранжирование (Uno-C), калибровка O/E | Порог 24ч из val; показать, где достижимо формально | wear: K=3035 prec≥0.7; fire: K=152 prec 0.70 (recall 0.35); access/sensor — недостижимо на 24ч (база 1%) |
| Время прогноза < 5 мин | Сохраняется по умолчанию (inference контракт, GPU/CPU <~секунды на объект) | — | Плюс к надёжности |
| 4 направления (пожар/доступ/отказ/износ) | Остаются в панели как 4 сценария с разными операционными точками | Общий 24ч-бенчмарк по 4 задачам | Не сводить в одну таблицу «все должны дать 24ч» |
| Автоматическое формирование заявок | Превентивная заявка из RBAM-плана (Сценарий 2) | Заявка «по алерту» (фолбэк) | Совместимо |
| Метрики тестирования holdout | Без изменений (защита от утечек) | — | — |

KPI-сет ядра: Precision@топ-K (по risk30/p24), Uno-C/IBS, ECE/O/E калибровки,
доля подтверждённых диспетчером, экономия на объездах/«тревог без эха»,
снижение доли отказов в окне при выполнении плана.

## 3. План действий по фазам

### Фаза A — Скоринг и согласование ядра (1–2 дня, до фиксации сервиса)
1. Определить **последствия (severity)** для RBAM-приоритета без реестра:
   - эвристика по типу канала/системы (дым/пожар > газ > охранные > насосы/вент > телеметрия);
   - вес по объекту (коллектор с людьми/транспортом vs отдалённый пикет) — таблица-маппинг;
   - коэффициент масштаба (сколько каналов/подчинённых систем).
   Артефакт: `research/docs/SEVERITY_MAP.md` (новая) + колонка «последствие» в топ-списках.
2. Зафиксировать KPI-сет и шаблон отчёта «состояние риска» (что показывать заказчику).
3. Прототип-макет: экран «Риск-карта» + «План ТО» поверх существующего дашборда
   (без изменения ML-пайплайна).

### Фаза B — Интеграция inference в сервис (1–2 дня)
1. Подключить `research/inference_contract.py` как библиотеку/адаптер в backend
   (load_model → predict_risk → calibrated_risk → топ-K).
2. REST-эндпоинты:
   - `GET /top-risks?task=fire|access|sensor|wear&period=7d|30d` — топ-K по risk30/p24, с факторами;
   - `GET /forecasts/{id}` — карточка (S(t), exp_days, риск, факторы, рекоменд. действие);
   - `POST /forecasts/{id}/decision` — подтвердить/отклонить, ответственный, комментарий;
   - `GET /maintenance-plan?quarter=...` — RBAM-план.
3. Сквозной сценарий «прогноз → алерт/план → диспетчер → решение → журнал»
   (обязательный из SERVICE_PLAN).

### Фаза C — Усиление сигнала на текущих данных (после релиза v0, P1)
1. **Sensor**: пер-типовые модели (дым/КД/газ/движение) — разные физики, разные пороги
   (ML_PLAN §2 подтверждает); стратифицированные метрики.
2. **Fire**: эхо-верификация (пары ИПР в 1–5 мин, окна) как фичи/атрибуты карточки;
   отдельный приоритет «ручной извещатель» vs «подтверждённый дым».
3. **Access**: sequential-фичи (дверь→движение 5–15 мин), night/weekend-baseline,
   объект×день аномалии (z/IF).
4. **Value-пайплайн**: тренды температуры/газа по объекту (7д отклонение) для деградации
   — рекуррентные признаки после стабилизации GBDT.
5. **L2-агрегация**: объектный индекс риска (правила/бустинг поверх L1) для карты.

### Фаза D — Fallback «буква ТЗ» (резерв, готовить заранее, но не в демо-базе)
1. Скрипт `report_tz_compliance.py`: для каждой задачи — P(≤24ч) на holdout,
   порог из val, Precision/Recall/PR-AUC, «достижимо/недостижимо» и причины.
2. Готовые честные формулировки:
   - wear: порог 24ч достигает Precision 0.7 с Recall ~0.8 (реальное соответствие);
   - fire: топ-152 → Prec 0.70 (Recall 0.35) — «соответствие по прецизии на ограниченном топе»;
   - access/sensor: на 24ч недостижимо — обоснование (база 1% / 0.3%, отсутствие СКУД/ОДС),
     контрпредложение: топ-K по risk30 + медиана дней.
3. Демо-режим «ТЗ-строгий»: если заказчик потребует именно 24ч — включаем эту панель
   с оговорками и не скрываем ограничения (доверие важнее метрики).

### Фаза E — Данные P2 (долг, интерфейсы готовы)
1. Адаптеры read-only: АРМ-Контроль (сварки/допуски), журнал ОДС, СКУД, реестр ремонтов/возраст.
2. При присоединении: обучение не перестраивается (feature pipeline заложен под joins,
   DATA_MATRIX.md), обновляются только инференс-контракт и отчёты.
3. Собирать подтверждения диспетчера с релиза (Фаза B) — это и есть будущий датасет
   для дообучения 24ч-задач.

## 4. Триггеры «переключиться обратно на ТЗ»

| Ситуация | Действие |
|---|---|
| Заказчик требует только P(≤24ч) и «строгие» 0.7/0.5 | Игрок: показать Фазу D (честные цифры); если не принимается — продавать как «риск-портфель + 24ч-панель в дополнение» |
| Заказчик признаёт RBAM-подход | Выключаем 24ч-панель из демо, оставляем в отчётах; ядро = Фазы A–C |
| Поступают данные АРМ/СКУД/ОДС | Включить Фазу E — возможно, вернуть 24ч-задачу в ядро по мере роста сигнала |

**Ничего не выбрасываем:** панели, модели, калибровки, inference-контракт и
holdout-артефакты остаются; меняется только приоритизация сценариев и способ презентации.

## 5. Риски плана

1. **«Недостаточность последствий»**: severity-маппинг без реестра — эвристика;
   пересматривать при получении реестра (P2).
2. **Претензия «это не то, что в ТЗ»**: закрывается Фазой D и заранее готовым
   script-отчётом соответствия + ссылкой на экспертную оценку (0.2: метрики не жёсткие).
3. **Деградация калибровки в проде**: drift-мониторинг (квартальные процентили p24/risk30, O/E) —
   контракт уже есть (`inference_contract.risk_drift_by_quarter`).
4. **Человек-в-цикле не заполняет подтверждения**: сделать подтверждение обязательным полем
   в карточке инцидента (иначе дообучение не начнётся).
