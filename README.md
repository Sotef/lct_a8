# lct_a8 — предиктивная аналитика аварий и отказов оборудования коллекторов АО «Москоллектор»

Веб-сервис, который превращает исторические и потоковые данные системы мониторинга СМВУ,
журналов ОДС и реестра оборудования в **прогноз риска аварий и отказов на горизонте до 30 дней
(шаг 6 часов)** и рабочий инструмент диспетчера: дашборд рисков, карта объектов, карточка прогноза
с факторами «почему», превентивные заявки на ТО/ППР, алерты, аудит решений.

**Модель предлагает — диспетчер решает.** Модель не подменяет решение человека: она даёт
вероятность события, горизонт, объяснение и рекомендованное действие, а финальный вердикт
(инцидент / ошибка / профилактика) фиксирует диспетчер и он же становится меткой для дообучения.

```
Направления прогнозирования (4):  пожарный риск · отказ датчика · несанкционированный доступ · износ инфраструктуры
Стек:  Python 3.12 · FastAPI · PostgreSQL 14 · SQLAlchemy 2 + Alembic · CatBoost (ML)
       SPA/PWA без сборки (ванильный JS + SVG-графики) · Docker Compose · nginx (TLS 1.2+)
Проверено:  71 pytest (41 unit + 30 «кнопочных») · E2E-прогон интерфейса 33 шага · DEPLOY VERIFY: ALL OK
```

## 1. Ключевые функции сервиса

| Функция | Что делает | Где в интерфейсе / API |
|---|---|---|
| **Дашборд рисков** | KPI по 4 направлениям (каналов, средний риск, высокие/критичные, число событий), тренд риска по 6ч-бакетам с выбором горизонта (1/3/7/30 дней), **сглаживанием (6 ч / 24 ч / 3 сут)** и режимом «средний/максимум»; средний считается по **«постоянной когорте»** каналов (состав сопоставим между бакетами — линия не скачет от «холодных» каналов); в подписи и тултипе — когорта, число каналов в бакете, среднее по всем каналам и сколько бакетов «тонкие» (мало каналов, точка ненадёжна) | Пульт; `GET /meta/summary`, `/meta/risk-history`, `/top-risks`, `/top-objects` |
| **«Прогноз ↔ реальное происшествие»** | Реальные происшествия журнала рядом с прогнозами и датами: что произошло, когда, было ли предсказано (прогноз от какой даты, за сколько часов, с какой вероятностью) или «пропущено моделью»; сводка recall/precision/медианное упреждение. Панель **не «пропадает» на тиках** (рисуется в живой узел + кэш последнего ответа), происшествия **за последние 24 ч показаны постоянно** (бейдж «24 ч»), а все происшествия **логируются во вкладку «Система»** (логгер `incident` + аудит `incident.journal`) | Пульт (карточка внизу); `GET /meta/events`; Система → Системный лог / Аудит |
| **Карта объектов и граф систем** | Дерево/список объектов с риском по направлениям, схема связности «объекты ↔ пикеты» (тег `p3`), подсветка соседей, L2-риск | Карта, Граф; `GET /objects`, `/objects/graph` |
| **Карточка прогноза** | Вероятности P(≤24 ч), P(≤72 ч), risk30, калиброванная вероятность, кривая S(t) 6ч→30 дней, E[время до события], SHAP-факторы «почему», класс события (авария/инцидент), история прогнозов канала, история решений, 3 кнопки решения | Карточка прогноза; `GET /forecasts/{id}`, `/forecasts/{id}/factors`, `/forecasts/{id}/facts` |
| **Решение диспетчера** | Подтвердить (инцидент) / Отклонить (ошибка, ложное срабатывание) / Профилактика (ППР, с датой выезда) → запись в журнал решений и аудит, метки для дообучения, при «профилактике» создаётся заявка | `POST /forecasts/{id}/decision` |
| **Превентивные заявки (ТО/ППР)** | Канбан-доска (предложена → назначена → в работе → выполнена/отменена), **план ТО по нормативному сроку ТО и возрасту оборудования** (возраст — по первой записи датчика), авто-формирование с порогом по классу последствия и ресурсным ограничением, **анти-«прыжки» сроков (гистерезис + заморозка даты диспетчера)**, график обслуживания **по «выездам»** (объект × дата), исполнитель, дата выезда, комментарии с автором и временем, «что устранено», фото с объекта, офлайн-действия с идемпотентностью | Заявки, План ТО; `GET/POST/PATCH /maintenance/*`, `/maintenance-plan` |
| **Алерты** | Кандидаты на уведомление по P(событие ≤ 7 дней), журнал отправленных алертов, порог и «тишина» 12 ч, веб-пуши (VAPID) и фолбэк-поллинг, отметка реакции диспетчера | Алерты; `GET /alerts`, `/push/*`, `POST /admin/alerts/run` |
| **Маршрут движения нарушителя** | По охранным сработкам объекта (люк, аварийный выход, дверь, движение, стекло) — упорядоченная цепочка точек с временем и пикетами: разновидность аварии «террор, проникновение нарушителя» | Карточка объекта; `GET /objects/{id}/security-route` |
| **Роли и аудит** | RBAC: техник (свой район), диспетчер, центральный; аудит всех действий (вход, решения, заявки, админ-операции), request-id в логах, живой системный лог | журнал аудита, «Система»; `GET /audit`, `/admin/logs*` |
| **Реплей-демо и живая подача** | Сим-часы двигают «сейчас» на 6 ч за тик (скорость 1×–8×, пауза, шаг, «Заново с января»), пересчёт прогнозов на каждом бакете; режим `SIM_FEED=1` — сервис сам читает грязный журнал СМВУ потоком и пересобирает признаки | «Система»; `POST /admin/clock/*`, `GET /meta/clock` |
| **Мониторинг и эксплуатация** | Health-check, статус источников данных, реестр моделей с метриками, drift по кварталам (процентили p24/risk30), перезагрузка моделей без рестарта | `GET /health`, `/admin/system`, `/admin/models`, `/admin/drift`, `/admin/data/status` |
| **Мобильный профиль (PWA)** | Адаптивная вёрстка, нижнее меню и bottom-sheet, карточки вместо таблиц, офлайн-очередь действий, установка как приложение, push-уведомления, съёмка фото | телефон/планшет; `GET /meta/client-config` |

## 2. Ключевые параметры проекта

| Параметр | Значение |
|---|---|
| **Направления прогнозирования** | `fire` — пожарный риск; `sensor` — отказ датчика; `access` — несанкционированный доступ; `wear` — износ инфраструктуры |
| **Событие (цель) по направлениям** | `fire` — серия «серьёзных» тревог (подтверждённое задымление ≥2 дымовых канала объекта за бакет **или** «Рычаг сдернут»); `sensor` — статусы «Неисправен/Обесточен/Отключено устройство»; `access` — серия охранных тревог (дверь/АВ/люк/движение/стекло); `wear` — серия неисправностей насосов, вентиляторов, фаз |
| **Горизонт и шаг** | до **30 дней** с шагом **6 часов** (120 шагов); отдаются P(≤24 ч) = `p24`, P(≤72 ч) = `p72`, P(≤7 дней) = `p7d`, риск 30 дней = `risk30` (+ калиброванный для `access`), E[время до события] = `exp_days` |
| **Алгоритм** | **CatBoost** — модель дискретного hazard (время до события, цензура), одна модель на направление; 4 обученные модели `.cbm` + калибровка `calib30_access.pkl` |
| **Число признаков (X)** | `fire` 137 · `access` 101 · `sensor` 95 · `wear` 64 — из них объектных агрегатов `*_об_б*`: 73 / 55 / 49 / 30 |
| **Данные** | журнал СМВУ 2019–2026 (≈16 ГБ распакованных CSV, пригодно к обучению ≈7,5 лет); справочники каналов/объектов; 6ч-панели «канал × бакет» (например `wear`: 1,6 млн строк, 1491 канал, 10 934 бакета); 19 типов датчиков (13 представлены ≥100 каналами) |
| **Сплит и защита от утечек** | train ≤ 2024 · validation 2025 · test (holdout) 2026; кампанийные недели (ППР/проверки) исключаются; окна признаков — «прошлое + текущий бакет»; z-статистики только по train; целевые и служебные колонки исключены из X |
| **Метрики (holdout 2026)** | 24ч PR-AUC: `fire` 0,421 · `wear` 0,890 (главные); precision@50 = 1,00 у fire/wear; K@precision≥0,7: fire 152, wear 3035; медианное E[дней до события]: fire 28,4 · wear 8,6; Uno-C 0,72–0,79; IBS 0,013–0,108 (полная таблица — §5) |
| **Приоритизация (RBAM)** | `score = risk × severity(тип датчика) × scale(объект)` → топ-риски, план ТО, авто-заявки (веса последствий: ручной извещатель 0,95; дым 0,85; газ/насос 0,80; затопление 0,75; люк 0,70; дверь/АВ/стекло 0,60; движение 0,55). Порог авто-заявки — свой на направление и ослабляется по severity (`base × SEVERITY_REF/severity`), ограничение — ресурс (ёмкость за тик + near-term cap), а не top-K. Подробно — [§8](#8-план-то-приоритизация-заявок-и-устойчивость-сроков) |
| **Классы событий** | авария = угроза жизни (пожар, наводнение, газ, террор, аномальная температура); инцидент = потеря связи/электроснабжения («слепые зоны»), косвенно допускает аварию |
| **Режимы работы** | демо-реплей 2026 с сим-часами (`SIM_CLOCK=1`, каждый тик двигает «сейчас» на 6 ч сим-времени) и живая подача из журнала (`SIM_FEED=1` — чтение грязного CSV потоком, агрегация, пересборка признаков, инференс текущего бакета) |
| **Производительность** | инференс одного бакета: агрегация + пересборка признаков + 4 модели — секунды на CPU; шаг прогноза 6 ч; API обслуживает ≥20 одновременных пользователей (async + пул соединений) |
| **Развёртывание** | Docker Compose: `api` (FastAPI + SPA/PWA) на `:8000`, `postgres` (PostgreSQL 14) на `:5432`, опционально `proxy` (nginx, TLS 1.2+) на `:8443`/`:8080` |
| **Аутентификация** | JWT (access 30 мин / refresh 7 дней), RBAC (`tech` / `dispatcher` / `central`), rate-limit на вход; LDAP/AD — read-only адаптер (на MVP локальные пользователи + демо-роли) |

        │ задымлений · серьёзн_ручной · тревог_дым/тепло/дверь/движение ·       │

        └────────────────────────┬───────────────────────────────────────────────────────┘

## 4. Данные

| Источник | Формат / объём | Как используется |
|---|---|---|
| Журнал СМВУ | `research/dataset/ext-journal-{2019…2026}.csv` (≈15,9 ГБ распакованных; одна схема на год) | события тревог: `ид_события`, `ид_канала_данных`, `дата`, `время`, `тревожное` (t/f), `значение_датчика` — основа всех признаков |
| Справочник каналов | `справочник_каналов_датчиков.csv` | `ид_канала_данных → тип_датчика, ид_объект, тег p1..p5, инж. система` — ключ «датчик ↔ объект» |
| Справочник объектов | `справочник_объектов_диспетчер.csv` | иерархия (район → камеры/объекты) для карты, RBAC по району, группировок |
| Графики ТО/ППР заказчика | «График ППР АКМ на 2026» и др. | `research/planned_work.py` → календарь ISO-недель: окна снятия/поверки датчиков метана и плановых работ |
| Решения диспетчера | таблица `decisions` (БД) | обратная петля ground-truth: подтверждение/отклонение/профилактика → метки для дообучения |
| P2 (данных пока нет) | АРМ-Контроль, журнал ОДС, СКУД, реестр ремонтов, РТЭКК | интерфейсы адаптеров готовы (`research/docs/ADAPTERS_README.md`), в признаках и метках не используются |

**Особенности данных, влияющие на модель**

* **Разреженность.** Панель «канал × бакет» собирается из журнала, поэтому строки есть только там, где по каналу были записи: для `wear` — 1,6 млн строк на 1491 канал × 10 934 бакета (плотность ≈9,8%, медиана 83 канала на бакет). Молчащие каналы в текущем бакете прогноза не получают.
* **Кампании проверок.** Периоды массовых срабатываний (пик 2021W17–W22 после ППР №1479 и СП 484/485/486 МЧС, плановые ППР и поверки) — **не аварии**: помечаются признаком `аномально` и исключаются из обучения и метрик (`research/data_utils.CAMPAIGN_WEEKS`).
* **Аномальные значения и статусы** (`−100`, `255`, «Обесточен», «Отключено устройство») трактуются как коды производителя/контроллера; словарь статусов — в `research/docs/DATA_REPORT.md`.
* **Разбиение по времени:** train ≤ 2024, validation 2025, holdout 2026 — модель оценивается на данных, которых не видела.

**Что лежит в git, а что нет**

| В репозитории (≈33 МБ) | Назначение |
|---|---|
| `research/models/tte_{fire,access,sensor,wear}_discrete_hazard.cbm`, `calib30_access.pkl` | обученные модели и калибровка |
| `research/dataset/справочник_*.csv` | справочники → `objects_ref` / `channels_ref` при старте |
| `services/data/raw/buckets_2026.parquet` | сырой 6ч-кэш 2026: из него на первом запуске собираются панели |
| `services/data/z_stats_*.csv`, `_features_schema.json`, `cat_codes_*.json`, `l2_object_risk.parquet` | train-статистики z, схема признаков, коды категорий, L2-риски |

**6ч-панели (≈319 МБ) — в Git LFS** и продублированы в публичном датасете Hugging Face `sotef/lct`.
Забрать их можно любым способом: `git lfs pull`, `services/scripts/fetch_demo_data.py --hf sotef/lct`
(режим файлов — `--hf-files`, архив — `--url <demo-data-2026.zip>`), а в Docker вообще ничего делать
не нужно — контейнер скачает их сам при первом старте (см. [§6](#6-быстрый-деплой)).

**Не в git** (и для демо не требуется): исходные журналы `ext-journal-*.csv` (нужны для загрузки новых
данных и переобучения), БД, логи, TLS-ключи. Если панели не пришли и сети нет — сервис пересобирает их
из raw-кэша `services/data/raw/buckets_2026.parquet` при первом запуске (дольше).

## 5. Модели и методы обучения

### Постановка задачи

Прогноз «случится ли событие» плохо отвечает на вопрос диспетчера «когда», поэтому задача
сформулирована как **анализ выживаемости (time-to-event)**: для каждого канала оценивается время до
следующего события с учётом цензуры (наблюдение кончается раньше события). Модель **дискретного
hazard** выдаёт S(t) — вероятность «дожить без события» по 6-часовым шагам на 120 шагов вперёд
(30 дней), из которой получаются операционные величины:

```
p24      = 1 − S(шаг 4)      P(событие ≤ 24 ч)       — «горит ли завтра»
p72      = 1 − S(шаг 12)     P(событие ≤ 72 ч)
p7d      = 1 − S(шаг 28)     P(событие ≤ 7 дней)     — алерты диспетчеру
risk30   = 1 − S(шаг 120)    риск события за 30 дней — приоритизация ТО/ППР
exp_days = Σ S(t) / 4        E[время до события] в днях (RMST)
```

### Выбранные модели

| Направление | Модель | Калибровка risk30 | Почему так |
|---|---|---|---|
| `wear` (износ) | CatBoost, discrete hazard (1000 итераций / lr 0,03 / глубина 10) | нет (raw) | лучший результат и устойчивость: 24ч PR-AUC 0,890; PR 48ч/7д/30д = 0,74/0,93/0,97; Uno-C 0,760 |
| `fire` (пожарный риск) | CatBoost, discrete hazard | нет (raw) | 24ч PR-AUC 0,421 при базе 1,53% (lift ≈27×), precision@50 = 1,00, K@precision≥0,7 = 152 |
| `sensor` (отказ датчика) | CatBoost, discrete hazard | нет (raw) | 24ч PR-AUC 0,012 при базе 0,31% (lift ≈4×), Uno-C 0,723 — вспомогательный сигнал |
| `access` (НСД) | CatBoost, discrete hazard | **да** (`calib30_access.pkl`, per-bin) | ранжирование слабое (PR-AUC 0,030 при базе 1,01%) — фундаментально: нет ground-truth по реальным проникновениям (СКУД/допуска/камер нет), поэтому оценка калибруется и подаётся как уровень риска |

Почему **CatBoost**: сравнивались LightGBM и «голые» survival-модели по PR-AUC и Uno-C — бустинговые
реализации близки, CatBoost устойчивее на редких событиях и корректно работает с категориальными
признаками (объект, тип датчика). Отклонённые эксперименты задокументированы в `research/docs/ML_PLAN.md`
(Часть II): сглаживание кумулятивного hazard — **отклонено** (0 из 5 сидов улучшений), окно 30 минут
для пожарного риска — **отклонено** (рвёт задымление); в отчётах фиксируется устройство обучения
(GPU/CPU даёт ±0,02 PR-AUC).

### Признаки: что именно «видит» модель

Строка = **канал × 6ч-бакет**. Обучение и онлайн используют **одну схему** (сервис сверяет имена и
порядок колонок при каждой сборке):

* **свой канал** — счётчики за бакет (`событий`, `тревог`, `неисправностей`, `шума` + панельные счётчики задачи: `задымлений`, `серьёзн_ручной`, `тревог_дым/тепло/дверь/движение`, `пр_разрывов`, `неисправн_дым`) и их **окна 12ч/24ч/48ч/7д/30д**;
* **z_событий** — пер-канальная нормализация частоты по train-статистикам (устойчивость к «шумным» каналам);
* **серийный контекст** — `дни_с_посл_неиспр`, `дни_с_посл_старта`, `в_серии_прокси` (серии = периоды активности канала);
* **объект целиком, но агрегированно** — `*_об_б`: суммы по всем каналам объекта за тот же бакет, их окна и `каналов_активных_об_б` (сколько каналов объекта активно/сработало);
* **календарь** — `час_бакета`, `день_недели`, `месяц`, `день_года` (+ признаки шага при развёртке горизонта: `шаг`, `час_шага`, `доля_горизонта`);
* **идентичность** — `ид_объект_code`, `тип_датчика_code`.

Итоговое число признаков: **fire 137 · access 101 · sensor 95 · wear 64** (из них объектных
агрегатов 73/55/49/30, канальных окон 45/30/30/20).

**Контроль утечек:** окна — только «прошлое + текущий бакет»; z-статистики — по train (≤2024, вне
кампаний); целевые и служебные колонки (`цель_6ч/12ч/24ч/48ч`, `event_flag`, `obs_days`,
`event_time_days`, `серия_старт`, `дни_до_серии`) исключены из X (`tte_pipeline.DROP_COLS`).

### Метрики на holdout 2026 (`research/dataset/final_metrics_v0.csv`, 20.09.2026)

| Задача | база 24ч | PR-AUC 24ч | prec@50 / @100 | recall@2000 | K@prec≥0,7 | ECE risk30 raw→cal | мед. E[дней] | Uno-C | IBS |
|---|---|---|---|---|---|---|---|---|---|
| **fire** | 1,53% | **0,421** | 1,00 / 0,97 | 0,71 | **152** | 0,078 → raw | 28,4 | 0,792 | 0,055 |
| **access** | 1,01% | 0,030 | 0,00 / 0,01 | 0,33 | — | 0,021 → **0,015** | 28,4 | 0,794 | 0,054 |

| **wear** | 12,7% | **0,890** | 1,00 / 1,00 | 0,75 | **3035** | 0,020 → raw | **8,6** | 0,761 | 0,108 |

`K@prec≥0,7` — сколько каналов нужно поднять в топе, чтобы удерживать precision ≥ 0,7 на горизонте
24 ч; этим числом настраиваются операционные пороги и объём превентивных заявок.

### Воспроизводимость

* Ноутбуки: `research/notebooks/00_data_pipeline` → `08…11` (baseline/горизонты/TTE) → `27/28/29` (задачи) → `30` (риск-портфель RBAM); обучение из CLI: `research/task_tte.py --task <fire|sensor|access|wear>`.

* Ядро (панели, признаки, инференс) сервис импортирует как библиотеку из `research/` — **одна реализация** для обучения и онлайна.

## 6. Быстрый деплой

### Вариант A — Docker (рекомендуется, 4 команды)

Нужен только **Docker Desktop** (Windows/macOS) или Docker Engine + Compose (Linux).
Python, venv, PostgreSQL, модели и демо-данные ставить/качать не требуется: код и артефакты —
в репозитории, а 6ч-панели контейнер скачает сам при первом старте.

```powershell
git clone https://github.com/Sotef/lct_a8.git
cd lct_a8\services
copy .env.docker.example .env        # bash: cp .env.docker.example .env
docker compose up -d --build
```

> **Демо-данные подтягиваются сами.** В `.env.docker.example` уже задан
> `DEMO_DATA_HF=sotef/lct` (публичный датасет Hugging Face, скачивание без токена).
> На старте entrypoint вызывает `fetch_demo_data.py --check`, и если чего-то не хватает —
> в том числе если вы клонировали **без** `git lfs pull` (файлы-указатели LFS распознаются) —
> скачивает `demo-data-2026.zip` и распаковывает в `services/data/`, не перезаписывая
> существующее. Переменные: `SKIP_DEMO_FETCH=1` (не ходить в сеть), `DEMO_DATA_URL=<URL>`
> (своя ссылка), `DEMO_DATA_TIMEOUT=60`. Логи: `docker compose logs api | Select-String entrypoint`.

> Нужны панели и на хосте (локальный запуск без Docker)? `git lfs install && git lfs pull`
> либо `services/scripts/fetch_demo_data.py --hf sotef/lct`. Если данных нет вообще и сети
> нет — панель соберётся из `data/raw/buckets_2026.parquet` при первом старте (дольше).
> Полный разбор способов доставки (LFS / Hugging Face / Release) — `services/README.md`
> → «Демо-данные 2026».

## 8. План ТО: приоритизация заявок и устойчивость сроков

Модуль превентивных заявок (`services/app/services/maintenance_service.py`) — это не «слепой top-K
по риску», а риск-ориентированная приоритизация с нормативным сроком, ресурсными ограничениями
и защитой от «прыжков» графика.

### 8.1 Возраст оборудования (реестр не используется)

Реестр оборудования (даты ввода в эксплуатацию, история ремонтов) заказчик не даёт, поэтому
**возраст = «сейчас» − первая запись с этого датчика за всё доступное время (2019…2026)**.
Артефакт `services/data/channel_first_seen.csv` собирается скриптом
`services/scripts/build_channel_meta.py` из помесячных бакетов research по всем годам
(8 165 каналов; медианный возраст на 01.01.2026 ≈ 5,1 года). Если канал в истории не встречался —
возраст «—», и логика плана работает без него.

### 8.2 Нормативный срок ТО

`services/app/services/to_norm.py` задаёт периодичность ТО по типу датчика (откат — по направлению):
пожарная автоматика и механика (насосы/вентиляторы/фазы) — ТО **2 раза в год (180 дней)**,
СКУД/КИП/двери/люки/температура — **1 раз в год (365 дней)**. Нормативный срок `norm_due` — ближайшая
дата ТО по периодичности, отсчитанная от первой записи датчика. Значения — эвристика v1, настраивается
(`NORM_PERIOD_DAYS_BY_TYPE` / `NORM_PERIOD_DAYS_BY_TASK`).

> Ограничение: график плановых работ приходит с анонимизированными объектами («Объект N») без
> маппинга на `ид_объект` (см. `research/planned_work.py`), поэтому помесячные окна ППР **по объекту**
> не применяются — периодичность берётся из справочника каналов (тип датчика/системы).

### 8.3 Дата плана: `min(прогноз, норматив)`

`plan_date = min(bucket + clamp(exp_days, 1, 90), norm_due)` — выезд **не позже любого из двух сроков**:
если модель ждёт деградацию раньше планового ТО — едем раньше (внеплановый выезд), иначе — штатное окно ТО.
Горизонт (`plan`) остаётся прежним контрактом: «текущий квартал» (<7 дн), «следующий квартал» (<21 дн),
иначе «плановый год». Пример: датчик 5 лет наблюдался, прогноз «отказ через 60 дней», норма «через 20 дней» → план **20 дней**.

### 8.4 Почему и как приоритизируются заявки

Базис — RBAM: `score = risk_used × severity(тип датчика) × scale(объект)` = вероятность × тяжесть × масштаб.

- **Порог вероятности — свой для направления** (`AUTO_TICKETS_MIN_RISK_BY_TASK`): у моделей разная шкала
  (калибрована только `access`, у `fire`/`wear` вероятности крупнее), единый порог сравнивал бы несравнимое.
  Дефолты: `fire 0.30`, `wear 0.50`, `access 0.45`, `sensor 0.45`.
- **Поправка на класс последствия**: `eff = base × (SEVERITY_REF / severity)` — чем тяжелее тип датчика
  (газ, ручной извещатель, насос), тем при меньшей вероятности заводим заявку; лёгкие типы — при большей.
- **Ограничение по ресурсу, а не «слепой top-K до дедупа»**: не более `AUTO_TICKETS_TOP_K` новых заявок
  за тик и не более `AUTO_TICKETS_NEAR_CAP` открытых near-term заявок (текущий+следующий квартал) на задачу.
- **Кампании/ППР не превращаются в заявки на ремонт**: бакеты «кампанийных» недель
  (`prediction.campaign = 1`) пропускаются — это плановая проверка, не отказ.
- **Дедупликация**: одна открытая заявка на `канал × направление`; приоритет `high/medium/low` — по риску
  и горизонту плана (`high`: risk ≥ 0.8 / p72 ≥ 0.5 / план ≤ 7 дней при risk ≥ 0.5).

### 8.5 Как избегаем «прыжков» графика

1. **Дата плана привязана к нормативу** (месяцы), а не только к `exp_days` (дни) — мелкие колебания
   модели не двигают выезд.
2. **Гистерезис** (`PLAN_HYSTERESIS_DAYS`, по умолчанию 5 дней): срок открытой и никем не назначенной
   заявки (`suggested`, без `scheduled_at`) обновляется только если уехал больше порога.
3. **Заморозка человеческого решения**: если диспетчер назначил `scheduled_at` или статус ≠ `suggested`,
   модель срок не меняет вообще.
4. **Прозрачность**: в заявке хранятся `age_days`, `norm_due` и JSON-`rationale` (прогноз/норматив/возраст/
   severity/эффективный порог/кампания); в карточке заявки — блок «почему такая дата».
5. **Группировка «выездов»**: график обслуживания группирует заявки по дате плана → объекту
   (один выезд = все датчики объекта), а не N отдельных строк.

## 10. Ответы заказчика и терминология

По письменным ответам заказчика (28.09.2026) в сервисе реализовано следующее
(полный разбор «что подтвердилось / что поменяли / что осталось» — `research/docs/CUSTOMER_ANSWERS.md`):

* **«Тревожное сообщение»** — запись журнала с `тревожное = true`; сервис не переводит её в инцидент автоматически: диспетчер проводит проверку и выбирает «Подтвердить (инцидент)», «Отклонить (ошибка/ложное)» или «Профилактика (ППР)».
* **Классы событий** (`app/services/alarm_service.py`, ручка `/objects/{id}/alarm-classes`): `авария` = угроза жизни — пожар, наводнение, газ, террор, аномальная температура; `инцидент` = потеря связи/электроснабжения («слепые зоны»), косвенно допускает аварию. Класс и группа показываются в карточке прогноза и в топах.
* **Охранные сработки** (люк, аварийный выход, дверь, движение, стекло) — разновидность аварии «террор, проникновение нарушителя»; по ним строится **маршрут движения нарушителя** (`GET /objects/{id}/security-route`, блок в карточке объекта).
* **ППР vs ТО**: серии сработок — это планово-предупредительные работы; массовые сработки помечаются признаком `аномально`, исключаются из обучения/метрик и отдельно показываются в панели фактов как «ППР».
* **Перечень ремонтов** по «Неисправен» (автомат, кабель, контактор, модуль связи, питание шкафа) — справочник «что устранено» при закрытии заявки; значение попадает в историю заявки и аудит.
* **Глоссарий каналов** (подтверждён): РО/АО — рабочее/аварийное освещение (СП 265.1325800.2016), ФРО/ФАО — их фидеры, ГРО — группа рабочего освещения, ФВ — фидер вентиляции, В23 — вентилятор, ФАНС — фидер автоматической насосной станции, ОЗК — огнезадерживающий клапан, ЩАП — щит аварийного питания с АВР, ФТС — фидер теплосети, ПУИ — пульт управления индикацией; «ПК» в названии фидера — что питает фидер; шаг пикета ≈10 м (может отличаться).

## 12. Ограничения и бэклог

**Ограничения моделей (честно)**

1. `access` (НСД) и `sensor` (отказ датчика) — слабые модели: 24ч PR-AUC 0,030 и 0,012 при базах 1,01% и 0,31%. Причина фундаментальная: нет ground-truth (журналы допусков/СКУД/камер, реестр ремонтов), нет внешних триггеров (АРМ-Контроль, погода). Модель используется как уровень риска, а не как «приговор».
2. Панель разреженная (≈10% «канал × бакет»): молчащие каналы в текущем бакете прогноза не получают — молчание датчика как ранний признак отказа модель видит лишь косвенно.
3. Абсолютные вероятности малы (2–13% за 24 ч) и у каждой задачи своя калибровка; операционные пороги настраиваются отдельно (по умолчанию — рабочая точка из `K@prec≥0.7`).
4. Маршрут нарушителя строится по 6ч-бакетам (в сервисной БД агрегаты, не сырые события) и в виде цепочки точек с пикетами — гео-координаты пикетов в данных не подтверждены.
5. Кампании ППР исключаются из метрик: это правильный подход для честных цифр, но означает, что сервис не «предсказывает» плановые проверки — их он показывает отдельной пометкой.
6. **Возраст оборудования** — не из реестра (его не дают), а по первой записи датчика за всё время (2019–2026). Это нижняя оценка возраста: датчик мог быть смонтирован раньше, чем появилась первая запись в журнале.
7. **Нормативная периодичность ТО** — эвристика v1 по типу датчика/направления. Помесячные окна ППР по объекту не применяются: график работ приходит с анонимизированными объектами («Объект N») без маппинга на `ид_объект` (см. `research/planned_work.py`).

**Бэклог (по приоритетам)**

* **P1.** Подключить внешние источники (АРМ-Контроль, журнал ОДС, СКУД, реестр ремонтов, РТЭКК) — самые ожидаемые улучшения: корреляция пожарного риска со сварочными/горячими работами; отличение проникновения от тестов; метки «нужен ремонт».
* **P1.** Обратная петля обучения: дообучать модели на подтверждениях диспетчера (`decisions`) — метки уже собираются.
* **P2.** Плотная сетка «канал × бакет» для молчащих каналов (сделает задачу «отказ датчика» существенно сильнее) и признаки «соседних каналов того же типа».
* **P2.** Признак «слепые зоны» (одновременная потеря связи/электроснабжения по объекту → косвенный риск аварии) — идея из ответов заказчика.
* **P2.** LDAP/AD вместо локальных пользователей, keycloak-подобный SSO; полноценный TLS-сертификат вместо самоподписанного для демо.
* **P2.** Внешний трекер заявок (HelpDesk) вместо внутренней таблицы; SMS/бот как аварийный канал уведомлений.
