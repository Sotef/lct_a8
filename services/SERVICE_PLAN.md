# SERVICE PLAN — веб-сервис предиктивной аналитики (уточнён по итогам 16.09)

Версия: 0.1 · Дата: 17.09.2026 · Backend & Web Service Team

## 1. Цель и рамки MVP (по итогам встречи с экспертами)

MVP — **не** «вся промышленная система», а несколько проработанных сценариев:

- прогноз отказа/инцидента по типам (старт — «износ»/wear, потом доступ и пожар-риск);
- **карточка прогноза/инцидента** (см. §5) + интерфейс диспетчера;
- **журнал прогнозов** (что предсказали, когда, кто посмотрел);
- **подтверждение/отклонение прогноза** — это будущая разметка для дообучения;
- REST API + рекомендация по превентивной заявке.

Разрешены (и приветствуются для демо): эмуляторы событий, демо-роли, тестовая
авторизация, генератор реалистичных событий (не «случайные числа»), воспроизведение
исторических последовательностей.

## 2. Роли и авторизация

- Авторизация: **LDAP-совместимый каталог, включая Active Directory** (TLS 1.2+).
- Базовая модель — **3 роли**:
  | Роль | Видит | Может |
  |---|---|---|
  | **Техник** | объект/комплекс коллекторов, локальные данные | подтверждать состояние на объекте |
  | **Диспетчер района** | объекты района и инж. системы | контроль событий района |
  | **Центральный диспетчер ОДС** | предприятие целиком, все системы/датчики/пороги | полный доступ, настройка порогов |
- Доп. дробление по подсистемам (пожар/охрана/газ) не обязательно.
- Полной интеграции с LDAP в прототипе нет → **имитация**: локальная авторизация,
  демо-роли, разграничение прав, тестовые группы. Роль «дежурный инженер» = роль диспетчера.

## 3. Одновременная работа диспетчеров

- Все видят один инцидент; **жёсткая блокировка не нужна**.
- В карточке журналируется: кто **начал** обработку, кто **подтвердил**, кто выполнил
  действие, **когда** выполнено; отображается ответственный.
- Все действия пользователей пишутся в audit-лог (RBAC + аудит по ТЗ).

## 4. Карта объектов

- Полное гео не требуется. Достаточно **схематичной линейной карты**:
  коллектор как линия → пикеты (шаг 10 м; для демо допустим другой шаг) → объекты →
  каналы → тревоги/прогнозы на линии.
- При желании — условные координаты, МСК (без преобразования в WGS84 на старте).
- Ключ привязки: `ид_объект` (подтверждён экспертами), пикеты — по `p3` (при наличии).

## 5. Карточка прогноза / инцидента (обязательный сценарий демо)

| Блок | Поля |
|---|---|
| Объект | объект (диспетчерский `ид_объект`), инж. система, канал, адрес/пикет |
| Риск | тип риска, **вероятность события**, прогнозный горизонт, уровень риска |
| Почему | факторы риска (топ фич), сезонные/календарные факторы, исторические аналоги |
| Действие | рекомендуемое действие, необходимость проверки, **превентивная заявка**, связанная организация |
| История | связанные события, история тревог, ответы организаций |
| Решение | **подтвердить/отклонить** (ложная / реальный инцидент / профилактическое), ответственный, комментарий |

**Прогноз «срок до события» (слой 2, survival-модель `11_wear_tte`):**
в карточку выводим **оба** значения — «запас прочности» диспетчеру:
- кривую выживаемости S(t) (6ч/12ч/24ч/48ч/7д/14д) — разброс вероятностей по
  времени, медиану и доверительный интервал «дней до события»;
- **точечный предикт ровно на 24 ч**: `P(событие ≤ 24ч) = 1 − S(24ч)` с порогом,
  подобранным на внутренней валидации (`research/docs/PLAN_LAYER2_TTE.md`).

Примеры факторов для объяснения: падение температуры зимой, сезонные риски
подтопления, праздники, рост температуры (>100° ≠ пожар — возможна сварка/локальный
нагрев), частые вкл/выкл насоса, цепочка последовательных тревог (доступ).

## 6. Подтверждения → дообучение

- Подтверждённой разметки в данных нет (журнал ОДС — HelpDesk без интеграции).
- Один из главных продуктовых циклов: диспетчер подтверждает/отклоняет прогноз →
  сервис накапливает **решения оператора** → бэкенд предоставляет их как датасет
  для периодического дообучения моделей (research).

## 7. Обновление данных

- Загрузка журналов: автоматически / вручную / гибридно, по выбору времени загрузки.
- Если загрузка занимает несколько минут — **запускать вручную явной кнопкой**
  (пользователь понимает, что система занята). Потоковые события — через адаптеры.

## 8. Внешние интеграции (адаптеры, read-only)

Согласно ТЗ: интеграции — отдельными adapters, в режиме read-only. Для конкурса —
эмуляторы: генератор событий, воспроизведение исторических журналов, тестовые
допуски/заявки. Камеры НЕ интегрируются (только ручная пометка «камера проверена»).

## 9. Ограничения производительности (из ТЗ, обязательные к замеру)

- inference одного объекта ≤ 300 с;
- задержка обработки потоковых данных ≤ 300 с;
- ≥ 20 одновременных пользователей (WebSockets/FastAPI + PostgreSQL).

## 10. Упаковка и оценка (критично по отзывам экспертов)

Обязательный пакет: документация, запускаемый пакет, инструкции, описание
развёртывания (Docker). **Настоятельно:** видео-демо основных сценариев и, при
возможности, ссылка на живой стенд. Критерии оценки: полнота пакета, запускаемость,
соответствие ТЗ, роли, понятность интерфейса, объяснимость, практическая ценность.

## 11. Интерфейс — прочее

- Тёмная тема не обязательна (не снижает оценку).
- Мобильное приложение не обязательно (дополнение).
- Интерфейс не перегружать декором; приоритет — понятность и работа с инцидентом.

## 12. Чек-лист демо (закрытые сценарии)

1. Карточка прогноза: риск + горизонт + «почему» (факторы).
2. Диспетчер подтвердил/отклонил → запись в журнал прогнозов + аудит.
3. Два пользователя на одном инциденте (ответственный, без блокировки).
4. Схематичная карта: линия коллектора, пикеты, тревоги на линии.
5. Превентивная заявка формируется/рекомендуется из карточки.
6. REST API: `GET /predictions`, `GET /predictions/{id}`, `POST /predictions/{id}/decision`.
