# MOBILE_PLAN — мобильная версия сервиса (PWA). План реализации

Версия 0.2 · 27.09.2026 · Backend & Web Service Team
Связанные документы: `BACKEND_SPEC.md`, `FRONTEND.md`, `README.md`, `API_CONTRACT`-раздел §5 `BACKEND_SPEC`.

> **Решение (зафиксировано):** делаем **мобильную версию того же сайта** — адаптивный
> mobile-first профиль + **PWA** (установка на домашний экран, офлайн-кэш, офлайн-очередь
> действий, Web Push). Нативное приложение, бот в мессенджере и SMS **вне объёма** этой
> работы (обоснование — §12). Вся работа идёт в текущем репозитории, без смены стека:
> FastAPI + vanilla-JS SPA, REST `/api/v1`, JWT, RBAC, аудит — переиспользуются как есть.

**Кратко о выводах**

- На телефоне сейчас ломается не «всё», а конкретные виджеты: канбан, таблицы, карта/граф,
  шапка с чипами — их и правим (полный список §3).
- Главная ценность в подземке — **офлайн-first** (связи внутри нет), поэтому PWA с очередью
  действий и идемпотентной синхронизацией важнее любого мессенджера (§4.5, §6).
- Уведомления нужно перенести **на сервер** (правило «P(≤7д) ≥ 0.2 + тишина 12 ч» сейчас
  живёт в localStorage `notify.js`) — иначе дубли на устройствах и нет алертов при закрытом
  приложении (§4.6).
- Минимальный полезный объём — этапы 0–2 (≈ 9–13 дней): рабочий телефонный сценарий техника
  и диспетчера. Полный объём с PWA, офлайном и push — 5–7 недель (§10).

## 1. Цели, критерии успеха, вне объёма

**Цель.** Дать технику и диспетчеру полноценный **телефонный сценарий**: посмотреть свои
заявки и алерты, открыть объект/датчик, взять заявку в работу, закрыть её с фото и
комментарием, подтвердить/отклонить прогноз — в том числе **без связи** (в коллекторе нет
GSM/LTE/Wi-Fi), с синхронизацией при появлении сети.

Критерии успеха (проверяемые):

1. Полный сценарий техника («мои заявки → в работу → выполнено + фото») проходит на экране
   360×640 без горизонтального скролла и без «мелких» тап-целей (< 44px).
2. Сайт устанавливается на домашний экран (Android Chrome/Edge, iOS Safari «На экран
   “Домой”»), запускается офлайн — открывается оболочка + ранее загруженные данные.
3. Действия, сделанные офлайн, доезжают до сервера после появления связи, без дублей и с
   записью в `audit_log` (идемпотентность по `client_id`).
4. Алерт по недельному риску приходит **push-уведомлением** (Android) с deep-link на карточку.
5. Lighthouse (mobile) — Performance ≥ 85, PWA installable, a11y ≥ 90 на ключевых экранах.
6. Существующая десктопная функциональность не деградирует: `pytest`, `front_static_check`,
   `ui_contract_check`, `web_smoke.ps1 [-WithTimers]` остаются зелёными.

**Вне объёма этой работы:** нативные приложения, боты в мессенджерах, SMS, офлайн-карты
коллекторов, QR/NFC-метки (см. §12 — почему и когда вернуться).

## 4. Целевая архитектура мобильной версии

### 4.1 Брейкпоинты и стратегия layout

Не переписываем CSS с нуля: добавляем **мобильный слой** `css/mobile.css`, подключаемый
последним в `index.html`, и мобильные правила по «профилю устройства».

| Breakpoint | Что происходит |
|---|---|
| `≤ 1200px` (уже есть) | `grid2/grid2e/grid3` в одну колонку |
| `≤ 860px` (уже есть) | сайдбар → выдвижное меню, бургер |
| `≤ 720px` (**новый профиль «mobile»**) | включается мобильный профиль: `.m-*` правила, нижняя навигация, карточки вместо таблиц, drawer → bottom-sheet, чипы в отдельной прокручиваемой строке, `#bgfx` выключен |
| `≤ 560px` | KPI 1 колонка, компактные заголовки, скрываем второстепенные метрики |
| `≤ 400px` | ужимаем типографику на 1 шаг, прячем подписи у иконочных кнопок |

Признак профиля в DOM/JS: `document.documentElement.dataset.mode = "mobile" | "desktop"`
(выставляется по `matchMedia("(max-width: 720px)")` c подпиской на `change`) — чтобы
JS-разделы могли выбирать поведение (например, канбан → табы) и не плодить `if` по ширине.

Правила проекта: тап-цель ≥ 44×44px, минимальный шрифт 13px, контент не шире
`100vw` без горизонтального скролла, `env(safe-area-inset-bottom)` для нижнего меню,
`touch-action: manipulation` для кнопок, никаких hover-only действий.

### 4.2 Навигация: нижнее меню, роутер, deep links

- Нижняя навигация (4 таба, фиксированная, blur + safe-area): **Алерты · Заявки · Объекты ·
  Ещё**. Состав зависит от роли (`tech`: Мои заявки · Алерты · Объекты · Профиль;
  `dispatcher/central`: Алерты · Заявки · Объекты · Ещё).
- «Ещё» — bottom-sheet со второстепенными разделами (Пульт, Журнал, План ТО, Граф, Аудит,
  Система, Пользователи по RBAC) + переключатель направления, темы, «Обновить данные».
- Роутер менять не нужно: он уже hash-based (`#/section`) и перерисовывает `#pagebox`
  через `UI.stage()`/`UI.mount()`. Добавляем:
  - поддержку параметров в hash (`#/forecasts?task=wear&id=123`) для deep-link из push;
  - кнопку/жест «назад» в мобильной оболочке (история браузера работает автоматически);
  - открытие карточек по `#/forecasts/{id}` — уже частично поддержано через `state.navigate`.
- Push deep-link: `https://<host>/#/forecasts?id=123` → роутер открывает раздел и карточку.

### 4.3 Экраны (состав)

| Экран | Состав | Ключевые элементы |
|---|---|---|

### 4.4 PWA: манифест, service worker, стратегии кэша

Новые файлы: `app/web/manifest.webmanifest`, `app/web/sw.js`, `app/web/icons/*`
(192/512/масковый, `apple-touch-icon`), подключение в `index.html`
(`<link rel="manifest">`, `apple-mobile-web-app-*`, `viewport-fit=cover`).

Манифест: `name`/`short_name` «Москоллектор ОДС», `display: standalone`,
`start_url: /#/alerts`, `theme_color` темы `obsidian`, `background_color`,
`orientation: portrait-primary`, `shortcuts` (Алерты, Мои заявки), `categories`.

Service worker (`sw.js`), версионируемый константой `VERSION`:

| Запрос | Стратегия |
|---|---|
| `install` | precache оболочки: `/`, `/index.html`, `/css/*.css`, `/js/*.js`, `/manifest.webmanifest`, иконки — через `fetch(url, {cache:"reload"})`, чтобы обойти HTTP-кэш и получить свежие файлы; `skipWaiting()` |
| `activate` | удалить кэши с чужим `VERSION`, `clients.claim()` |
| навигация (HTML) | network-first → при офлайне отдать precached `/index.html` (SPA-оболочка) |
| `/api/v1/**` GET «справочных» данных (`/objects`, `/meta/tasks`, `/maintenance/tickets?mine=1`, `/forecasts/{id}`) | network-first с записью в кэш `data-vN`; при офлайне — из кэша + пометка «данные от <время>» |
| `/api/v1/**` POST/PATCH | **только сеть**; при офлайне — перехват и постановка в очередь (§4.5) |
| статика (`/css`,`/js`,`/icons`) | cache-first из precache |

Про уже сделанное: статика в `app/main.py` отдаётся с `Cache-Control: no-cache` — это
защищает **десктоп** от старого JS. Для SW это не конфликт: precache делается с
`cache:"reload"`, а «источник истины» для офлайна — кэш SW, версионируемый `VERSION`.
Обновление: `registration.update()` при возврате в фокус + тост «Доступна новая версия —
обновить» (кнопка: `skipWaiting` + reload), чтобы не работать неделю на старой сборке.

### 4.5 Офлайн-режим и очередь действий (главная ценность в подземке)

Хранилище: `IndexedDB` (обёртка `js/mobile/offline.js`, без внешних библиотек).

- **Кэш данных** `cache_data`: `my_tickets`, `objects`, `forecasts_cache`, метка `fetched_at`.
  В UI — плашка «офлайн · данные от 21:40».
- **Очередь** `outbox`: `{cid (uuid v4), ts, method, path, body, base_status, files[], attempts, last_error}`.
  Офлайн разрешаем: `PATCH /maintenance/tickets/{id}` (статус, комментарий, дата выезда),
  `POST /forecasts/{id}/decision`, добавление фото. `auto-generate` и админские ручки — только онлайн.
- **Отправка:** триггеры — событие `online`, возврат в фокус, «Синхронизировать сейчас»,
  периодический пинг (Chrome Android — Background Sync; iOS — только в фокусе). Перед
  отправкой — proactive `POST /auth/refresh`, если access истёк.
- **Идемпотентность (обязательна):** клиент шлёт `X-Client-Id: <cid>`; сервер хранит
  `processed_actions(client_id UNIQUE, user_id, path, created_at, response json)` и на повтор
  возвращает сохранённый ответ, не применяя действие снова. Без этого ретраи из подземки
  создадут дубли заявок/решений.
- **Конфликты:** клиент отправляет `base_status`; если на сервере статус уже другой — `409`
  + текущая карточка, UI: «заявка изменена другим пользователем: сейчас “В работе”» и выбор
  «обновить/перезаписать».
- **Аудит:** каждая синхронизация пишется в `audit_log` с `detail.source="mobile-offline"`,
  `client_id`, `offline_ts`, `synced_at` — видно, что действие сделано в поле без связи.
- **Фото:** сжатие на устройстве (canvas, длинная сторона ≤1280px, JPEG q≈0.72, ≤300 КБ),
  в очередь — Blob; при синхронизации `POST /maintenance/tickets/{id}/attachments` (multipart).
- **Индикация:** в шапке «нет связи» / «N действий ждут отправки»; бейдж на офлайн-изменённых
  карточках; ошибки синхронизации — в «Профиле» с кнопкой «повторить».

### 4.6 Web Push вместо поллинга (правило тишины переносим на сервер)

Сейчас правило живёт в браузере (`js/notify.js`: `p7d ≥ 0.2`, тишина 12 ч в
`localStorage mc_notify_log`, опрос `/top-risks` каждые 25 с). На телефоне это даёт три
проблемы: при закрытом приложении уведомлений нет; один датчик на двух устройствах даст два
уведомления; расход батареи. Переносим правило на сервер:

- Таблицы: `push_subscriptions` (§6.3) и `alert_log(task, channel_id, risk_value, sent_at, kind, user_id)`.
- Воркер `app/workers/alerts.py` (вызывается после каждого тика прогноза — хук в
  `prediction_service.compute_and_store_bucket` или в существующий `workers/scheduler.py`):
  берёт каналы с `p7d ≥ ALERTS_MIN_P7D` (0.2), исключает пары `(task, channel_id)` из
  `alert_log` моложе `ALERTS_SILENCE_HOURS` (12), рассылает push тем, у кого есть доступ к
  объекту (`scoped_object_ids`), пишет `alert_log` + `audit_log(action="alert.push")`.
- Payload: `{title:"Пожарный риск · ДУ объект Альфа", body:"P(≤7д)=0.34 · дымовой датчик",
  url:"/#/forecasts?id=123", tag:"wear|12345", renotify:false, ttl:43200, urgency:"high"}`
  (`tag` группирует по датчику, чтобы не спамить).
- Ручки: `GET /push/vapid-public-key`, `POST /push/subscribe`, `DELETE /push/subscribe`, `POST /push/test`.
- Зависимость: `pywebpush` (+`cryptography`) в `services/requirements.txt`. **Проверить
  офлайн-установку wheels в контуре заказчика**; резерв — минимальная реализация Web Push на
  `cryptography` + `http_ece` (тот же HTTP-протокол).
- Фолбэк: нет подписки/не доставлено → работает привычный поллинг (данные берём из `alert_log`,
  чтобы не дублировать); в «Профиле» — «Включить уведомления» с проверкой разрешения.
- Тихие часы (опционально `ALERTS_QUIET_FROM/TO`): обычные алерты молчат, «пожарный риск» и
  `risk30 ≥ 0.8` — всегда.

### 4.7 Мобильная аутентификация и сессии

- Текущее: JWT access 30 мин / refresh 7 сут, оба в `localStorage` (`js/api.js`). Для телефона
  это неудобно (ввод пароля в поле, долгая сессия) и небезопасно (токен доступен JS).
  **Рекомендация:** refresh-токен переводим в `HttpOnly` cookie (`SameSite=Lax`, `Secure`),
  access держим в памяти вкладки; добавляем CSRF-защиту (double-submit) — это улучшает и десктоп.
  Обратная совместимость: пока флаг `AUTH_COOKIE_REFRESH=0` — старое поведение.
- Мобильный профиль: `X-Client: pwa` → увеличенный TTL refresh (например 30 сут) и «сессия
  активна, пока приложение установлено».
- Быстрый вход (этап 2): PIN 4–6 цифр как локальный «замок» приложения; при установке PWA —
  WebAuthn (`authenticatorAttachment: "platform"`) для разблокировки сохранённого refresh.
  Пароль/AD-вход остаётся основным (по ТЗ — LDAP/AD), PIN — только удобство поверх.
- Выход: очищает IndexedDB-кэш, `outbox` (с предупреждением, если есть несинхронизированные
  действия), cookie/токены и подписку push (с подтверждением «выключить уведомления?»).

### 4.8 UI/UX-правила мобильного профиля

- Тап-цели ≥ 44×44, отступы между действиями ≥ 8px, `touch-action: manipulation`.
- Крупные заголовки-«шапки» разделов, sticky-поиск в списках, pull-to-refresh.
- Bottom-sheet вместо drawer/modal; закрытие свайпом вниз; «ручка» и заголовок.
- Состояния: skeleton при первой загрузке, «обновляем…» при фоновой, «офлайн · данные от …»,
  «N ждут синхронизации», пустые состояния по-русски (как сейчас в `UI.emptyState`).
- Тёмная тема по умолчанию, `color-scheme` уже есть; при `prefers-reduced-motion` — без анимаций.
- Производительность: `#bgfx` выключен, `data-tilt`/spotlight отключены, графики —
  уменьшенная высота и не более 1–2 в экране, `content-visibility: auto` для длинных списков.
- Доступность: контраст ≥ 4.5:1, увеличение до 200% без потери функций, `aria-label` у
  иконочных кнопок, фокус-ловушка в sheet, порядок табов логичный.

### 6.3 Новые таблицы (набросок DDL, PostgreSQL 12+ / совместимо с SQLite)

```sql
-- подписки на push
CREATE TABLE push_subscriptions (
  id         INTEGER PRIMARY KEY,                     -- SERIAL в PG
  user_id    INTEGER NOT NULL REFERENCES users(id),
  endpoint   TEXT NOT NULL UNIQUE,
  p256dh     TEXT NOT NULL,
  auth       TEXT NOT NULL,
  ua         VARCHAR(200),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_ok_at TIMESTAMPTZ, fails INTEGER NOT NULL DEFAULT 0
);

-- журнал отправленных алертов (заменяет localStorage-«тишину» notify.js)
CREATE TABLE alert_log (
  id         INTEGER PRIMARY KEY,
  task       VARCHAR(20) NOT NULL,
  channel_id VARCHAR(64) NOT NULL,
  object_id  VARCHAR(64),
  risk_value FLOAT NOT NULL,
  kind       VARCHAR(20) NOT NULL,          -- push | inapp
  user_id    INTEGER REFERENCES users(id),
  sent_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_alert_log_pair ON alert_log (task, channel_id, sent_at DESC);

-- идемпотентность офлайн-действий
CREATE TABLE processed_actions (
  client_id  VARCHAR(64) PRIMARY KEY,
  user_id    INTEGER REFERENCES users(id),
  path       VARCHAR(200) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  response   JSON
);

-- вложения (фото с объекта)
CREATE TABLE attachments (
  id          INTEGER PRIMARY KEY,
  ticket_id   INTEGER NOT NULL REFERENCES maintenance_tasks(id),
  filename    VARCHAR(200) NOT NULL,
  mime        VARCHAR(80) NOT NULL,
  size        INTEGER NOT NULL,
  sha256      VARCHAR(64) NOT NULL,
  uploaded_by INTEGER REFERENCES users(id),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Миграции: PostgreSQL — Alembic (`alembic/versions/0002_mobile.py`), SQLite — существующий
механизм `database._ensure_columns` + `CREATE TABLE IF NOT EXISTS` (как уже сделано для
`maintenance_tasks`/`object_risk_l2`), чтобы демо-БД обновлялась при старте.

## 7. Безопасность, аудит и соответствие ТЗ

| Требование ТЗ | Как выполняется в мобильной версии |
|---|---|
| TLS 1.2+ | обязательное условие для SW/Push и для работы по сети: TLS-терминация на reverse-proxy (nginx/IIS) либо `--ssl-keyfile/--ssl-certfile` у uvicorn; в `serve.py` — предупреждение при HTTP |
| RBAC | скоупы не меняются: `scoped_object_ids(user, db)` применяется и к `mine=1`, и к `/alerts`, и к вложениям (файл отдаётся эндпоинтом с проверкой, а не статикой) |
| LDAP/AD | вход остаётся через существующий адаптер; PIN/WebAuthn — только локальная разблокировка уже выданной сессии |
| Журналирование действий | каждое офлайн-действие пишется в `audit_log` при синхронизации с `source="mobile-offline"`, `client_id`, `offline_ts`, `synced_at`; push-рассылка — `action="alert.push"` |
| Идемпотентность/целостность | `processed_actions` + `X-Client-Id`; `base_status` защищает от «отката» чужих изменений |
| ПДн и офлайн-кэш | в IndexedDB хранятся только объекты/заявки/риски без ПДн третьих лиц; при выходе кэш и очередь очищаются (с предупреждением); на устройстве помечается «корпоративное устройство» |
| Защита файлов | только `image/*`, размер ≤ `ATTACH_MAX_MB`, проверка сигнатуры (magic bytes), SHA-256 в БД, отдача через RBAC-эндпоинт с `Content-Disposition: inline`, запрет исполнимых типов |
| Секреты | VAPID-ключи в `.env`, не в репозитории; `sw.js` не содержит секретов |
| Rate-limit | `POST /push/subscribe`, вложения и синхронизация — под общим лимитером; логин уже ограничен (`LOGIN_RATE_LIMIT`) |

## 11. Риски и митигации

| Риск | Влияние | Митигация |
|---|---|---|
| **iOS**: нет Background Sync, push только с 16.4 и после «на экран Домой» | офлайн-синхронизация и push на iPhone ограничены | синхронизация в фокусе + инструкция «установить на экран»; на iOS поллинг остаётся основным для алертов; для критичных алертов — дублирующий канал (SMS/внутренний бот) как отдельное решение |
| SW/push не работают по `http://<IP>` (не secure context) | на телефонах в сети не будет офлайна и push | обязательная TLS-терминация на прокси (или домен + сертификат); локально `http://127.0.0.1`/`localhost` — исключение для разработки |
| Конфликты офлайн-правок | «откат» чужих изменений | `base_status` + `409` + понятный диалог выбора; сервер всегда источник истины по статусу |
| Дубли действий при ретраях | двойные заявки/решения | `processed_actions` + `X-Client-Id` (обязательное требование, покрыто тестом) |
| `pywebpush`/wheels недоступны в офлайн-контуре | push не запустить | заранее собрать wheels в контуре, либо резервная реализация Web Push на уже имеющемся `cryptography` |
| Старый JS в кэше SW после обновления | странные баги у части пользователей | версионирование кэша + `registration.update()` + тост «обновить»; при этом HTTP `no-cache` для статики остаётся |
| Большая демо-БД SQLite (≈8 ГБ) | миграции/`ALTER TABLE` могут блокировать сервис | миграции — только при остановленном сервисе или в окно; новые таблицы создаются `IF NOT EXISTS` |
| Рост нагрузки от push-воркера | лишние запросы при 4 задачах × сотни каналов | батчинг, top-K по `p7d`, отправка только при смене «молчания», отдельный лёгкий воркер после тика |
| Тестирование SW/push в headless | часть сценариев не покрыть автоматически | ручной чек-лист на реальных устройствах (обязательная часть приёмки) + авто-проверка регистрации SW |
| Расширение объёма («заодно сделаем нативку») | срыв сроков | жёсткое «вне объёма» (§12) и решение по нативке только по метрикам PWA |

## 12. Что явно не делаем (и при каких условиях вернёмся)

| Вариант | Почему не сейчас | Когда вернуться |
|---|---|---|
| **Нативное приложение (Android/iOS)** | 1.5–3 месяца + сторы/MDM + поддержка версий ОС; дублирование UI | если PWA покажет: нужен доступ к камере в фоне, офлайн-карты коллекторов, QR/NFC-метки, фоновая синхронизация; делать через **Capacitor** поверх той же PWA |
| **Бот в мессенджере (MAX/Telegram и т.п.)** | внешний контур и ИБ режимного объекта; нет офлайна (в коллекторе связи нет); аудит и ПДн вне нашего контроля; слабый UI для таблиц/фото | если предприятие официально использует мессенджер и ИБ разрешит: только **внутренний** (self-hosted Mattermost/Rocket.Chat/TrueConf) или корпоративный шлюз, исключительно как транспорт «короткий алерт + deep-link в PWA», с маскированием ПДн и записью факта отправки в `audit_log` |
| **SMS** | платно за каждое сообщение, 70 символов, без состояния/вложений/офлайна; не решает задачу «работа в поле» | только как (а) страховочный канал аварийных уведомлений, когда push недоставлен, и (б) второй фактор при входе для тех, у кого нет корпоративного аккаунта |

## Приложение C. Чек-лист приёмки на устройстве

**Установка и оболочка**
1. Сайт открывается на Android Chrome и iOS Safari, вёрстка не «разъезжается».
2. Баннер/пункт «Установить приложение» есть; после установки ярлык и иконка корректны.
3. Приложение запускается в standalone (без адресной строки), safe-area не перекрывает меню.
4. Ни в одном разделе нет горизонтального скролла; тап-цели ≥ 44×44.

**Навигация**
5. Нижнее меню: 4 таба, активный подсвечен, работает история браузера («назад»).
6. «Ещё» открывается sheet, разделы фильтруются по роли (без «Системы» у диспетчера/техника).
7. Deep-link `#/forecasts?id=…` открывает раздел и карточку прогноза.

**Сценарий техника**
8. «Мои заявки» показывает только заявки текущего пользователя, сортировка — по сроку выезда.
9. «В работу» → статус меняется, бейдж исчезает, действие видно в журнале аудита.
10. «Выполнено» без комментария — блокируется; с комментарием — проходит.
11. Фото: камера/галерея открывается, фото сжимается (≤300 КБ), прикрепляется, видно в карточке.
12. Перенос даты выезда (диспетчер) сохраняется и отображается в списке.

**Офлайн (авиарежим)**
13. Плашка «офлайн · данные от <время>» появилась; ранее загруженные списки читаются.
14. Действие «В работу» + фото + комментарий ставятся в очередь, счётчик «N ждут отправки» растёт.
15. После включения сети — синхронизация автоматически; счётчик обнулился.
16. В журнале аудита — записи с `source=mobile-offline` и временем офлайн-действия.
17. Повторный запуск приложения не создаёт дублей заявок/решений (проверить по аудиту).
18. Конфликт: изменить ту же заявку на десктопе, затем синхронизировать телефон → понятное сообщение, без «отката».

**Алерты**
19. Разрешение на уведомления запрашивается по кнопке «Включить уведомления» в «Профиле».
20. Push приходит при **закрытом** приложении; тап открывает нужный прогноз.
21. Повторный алерт по тому же датчику не приходит раньше 12 ч (проверить по `alert_log`).
22. Два устройства одного пользователя не дают двух записей в `alert_log`.

**Прочее**
23. Тёмная тема и `prefers-reduced-motion` учитываются; фон-канвас на телефоне отключён.
24. Выход: предупреждение о несинхронизированных действиях, очистка кэша/очереди, снятие подписки.
25. Токен-флоу: сессия живёт после перезапуска PWA (по политике TTL), refresh не падает.
26. На экране 360×640 и планшете 768×1024 сценарий проходит без обрезки элементов.

   только внутренний контур (тогда push — только через self-hosted прокси, либо отказ в пользу

5. **Тихие часы и приоритеты алертов:** какие события можно не отправлять ночью?

7. **Сроки/приоритет:** нужен ли минимум (этапы 0–2, ≈2 недели) к ближайшей демонстрации или
   полный объём с офлайном и push?

| GET | `/meta/client-config` | пороги/TTL/фиче-флаги для мобильного клиента (без секретов) |
| GET | `/push/vapid-public-key` | публичный VAPID-ключ |
| POST/DELETE | `/push/subscribe` | регистрация/снятие push-подписки устройства |
| POST | `/push/test` | тестовое уведомление (при отсутствии VAPID/pywebpush — понятный ответ) |
| GET/POST | `/maintenance/tickets/{id}/attachments` | список/загрузка фото (проверка сигнатуры JPEG/PNG/WEBP, лимит `ATTACH_MAX_MB`) |
| GET | `/maintenance/attachments/{id}` | отдача файла с проверкой скоупа объекта |

### Бэкенд — правки
- `models_db.py`: таблицы `push_subscriptions`, `alert_log`, `processed_actions`, `attachments`.
- `maintenance_service.list_tickets`: `mine`, `scope=active`, `order=due`, курсорная пагинация (`next_cursor`/`has_more`).
- `maintenance_service.update_status` / `decision_service.create_decision`: в аудит пишутся `source="mobile-offline"`, `client_id`, `offline_ts`, `synced_at`.
- `api/maintenance.set_status`, `api/forecasts.decide`: идемпотентность по `X-Client-Id` (`processed_actions`) + оптимистичная блокировка `base_status` → `409 {code:"conflict", current:{…}}`.
- `services/idempotency.py`, `services/attachment_service.py`, `services/push_service.py`: новые сервисы.
- `workers/alerts.py`: серверное правило алертов + рассылка по подписчикам с учётом района; вызывается на каждом тике (`simclock`, `ingestion`) и вручную.
- `main.py`: роутеры `alerts`/`push`, отдача `/sw.js` (`Cache-Control: no-store`, `Service-Worker-Allowed: /`) и `/manifest.webmanifest`.
- `.env.example`: `PWA`, `ALERTS_*`, `VAPID_*`, `MOBILE_REFRESH_DAYS`, `ATTACH_*`.

### Тест на реальном телефоне

1. `ipconfig` → IP компьютера, на котором запущен Docker; телефон — в той же Wi-Fi/сети.
2. Откройте `http://<IP>:8000` — адаптивный UI: нижнее меню из 4 табов, «Ещё»
   (bottom-sheet), карточки вместо таблиц/канбана, карточка заявки, фото с камеры.
   Если порт закрыт: `netsh advfirewall firewall add rule name="LCT 8000" dir=in action=allow protocol=TCP localport=8000` (PowerShell от администратора).
3. Полный PWA-сценарий (установка, офлайн-очередь, Web Push) требует *secure context*:
   - **на компьютере** — `http://127.0.0.1:8000` + DevTools device mode (localhost безопасен,
     офлайн проверяется в DevTools → Application → Service Workers);
   - **на телефоне** — `docker compose --profile tls up -d --build` и `https://<IP>:8443`
     с **доверенным** сертификатом (самоподписанный Chrome не примет для service worker).
4. По `http://<IP>` браузер считает origin небезопасным → SW/PWA/офлайн/push не включатся
   (вёрстка и обычные запросы работают).
5. Приёмка по экранам — **Приложение C** (26 пунктов).

### Осознанные ограничения (честно)
- **PWA/push требуют HTTPS или localhost**: без них SW не регистрируется, работает фолбэк-поллинг `GET /alerts`.
- `pywebpush`/`py-vapid` **не входят** в `requirements.txt` (опциональны): без них `/push/*` отвечает корректно, но рассылка не выполняется (`sent=0`).
- Конфликт 409 разрешается диалогом «применить к новому состоянию / оставить»; автоматического мерджа нет.
- На iOS `Background Sync` недоступен — очередь отправляется по `online`/`focus`/таймеру/`visibilitychange`.
- Копия рабочей БД в WAL-режиме для внешнего процесса-читателя несовместима (нужен `VACUUM INTO`/checkpoint) — это ограничение среды, не сервиса.
